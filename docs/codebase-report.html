Reuse audit for future projects — what to keep, what to fix, what to add

Node 24 · TS 6 · Express 5 ~3,700 LOC src/ Mongoose 9 · Redis · BullMQ analyzed 2026-07-05
Verdict: this is a genuinely strong foundation — well above typical boilerplate quality. The architecture (typed ACL, module system, fail-fast config, unified envelope) is worth reusing as-is. But it is not internet-ready today: authentication is a placeholder, one security feature is silently broken (confirmed in the logs), and a few "fail-fast" claims have soft spots. Everything below is ranked so you can work top-down.

03 What's already best-practice — keep these

These patterns are the reusable value of the repo. Copy packages/ untouched into future projects, exactly as the README intends.

Three-layer ACL (the crown jewel)

Permissions checked at compile time (defineACL literal types), boot time (ungranted RAI throws), and runtime (one authorize middleware). Typo-proof by construction — rare even in commercial frameworks.

Fail-fast zod env validation

config/env.ts refuses to boot on bad config and prints the offending key + file path. No half-booted apps.

Unified response envelope

One { isOk, data, errors, meta } shape for success and failure, rendered by a single central error handler with per-request i18n. Body-parser errors mapped to clean 400/413s.

Production logging done right

Pino with secret redaction (authorization, cookie, password, token), correlation IDs, rotation, pretty-only-in-dev, PM2-aware process naming.

Soft-delete plugin quality

Uses $ne: true so legacy docs stay live, covers aggregations, offers .withDeleted()/.onlyDeleted() escape hatches, polymorphic deleted_by actor. Global registration before any schema compiles.

Queue architecture

Web = producer, dedicated worker = consumer. Sane BullMQ defaults (3 attempts, exponential backoff, TTL'd job cleanup). Mail rendered at call site so the worker never touches React.

Module system with real topo-sort

depends resolved with cycle detection; unknown deps throw. Models auto-load, i18n namespaces self-register, onInit ordered.

Graceful shutdown

SIGTERM/SIGINT drain HTTP → queue → mailer → Redis → Mongo, with a forced-exit deadline. Shared between web and worker entry points.

Secrets hygiene

Only .env.example is tracked in git; real env files and logs are ignored. JWT key generation scripted (yarn keys:jwt) with RS256 default.

Express 5 chosen well

Async handler rejections auto-forward to the error handler — no wrapper hell. Slowloris timeouts set on the HTTP server. trust proxy conservative by default.

04 Things to be cautious about

Ranked by severity. The top two block any internet-facing deployment.

Critical Authentication is a placeholder — any caller can claim any role

src/lib/access-control.ts:79–85

The authenticate middleware reads a plain x-roles request header and trusts it verbatim. curl -H "x-roles: sysadmin" grants full access to every route. The README documents this honestly, and the JWT helpers (helpers/jwt — sign/verify, access vs refresh typing, HS/RS/ES) are already built — they're just not wired in.

Fix: replace the header read with Authorization: Bearer parsing → verifyAccessToken() → populate req.auth from the token's claims. Then build the auth module (login / refresh / logout) and attach the already-exported authRateLimiter to it. This is the single highest-value task in the repo.

Critical Confirmed in logs Redis-backed rate limiting never engages — import-order bug

src/lib/security.ts:81–96 · evidence: logs/app-2026-06-29.log

The two limiters are built at module import time (top-level buildLimiter(...) calls). ES module imports are hoisted, so security.ts evaluates when Application.ts loads its imports — before bootstrapInfra() ever calls connectRedis(). isRedisConnected() is therefore always false at that moment, and both limiters silently fall back to the per-process memory store. Your own runtime logs prove it on every boot:

{"level":"warn","msg":"Rate limiter \"rl:global:\" using in-memory store (Redis not connected) — limits are per-process"}
{"level":"warn","msg":"Rate limiter \"rl:auth:\" using in-memory store (Redis not connected) — limits are per-process"}

Consequence: under PM2 cluster with N instances, the real limit is N × RATE_LIMIT_MAX, and limits reset on every reload. The README's "shared across the cluster" claim doesn't hold.

Fix: make store creation lazy — export a buildLimiters() factory called from createApp() (which runs after infra boot), or pass a lazily-resolved sendCommand that fetches the client per call. One-file change.

High One MongoDB query on every single request (resource toggle)

src/lib/access-control.ts:18–34

checkResourceEnabled runs Resource.exists({_id: rai, is_enabled: true}) as the first guard on every route, every request. It's indexed, but it still adds a DB round-trip of latency to all traffic and makes MongoDB a hard dependency of even cache-served endpoints. Ironically, the repo ships a perfectly good Cache layer that isn't used here.

Fix: cache the enabled-set (e.g. cache.wrap("resources:enabled", 30, ...) or an in-process map refreshed every N seconds / invalidated via Redis pub-sub when an admin toggles a resource). Fail-open or fail-closed is your call — decide explicitly.

High Module onInit failures are swallowed — "fail-fast" has a hole

src/lib/modules.ts:95–110

initModules catches every onInit rejection and only logs a warning. If core's resource sync fails (Mongo hiccup at boot), the app starts anyway — but with no Resource docs, checkResourceEnabled then 404s every route, and nothing in the logs above warn level explains why. That contradicts the fail-fast philosophy everywhere else in the codebase.

Fix: let onInit errors throw (aborting boot), or add a critical: true flag on the module contract so core-style modules abort while optional ones warn.

High CORS * + credentials is representable — and nothing stops it in production

src/lib/security.ts:32–42 · src/config/env.ts:30–31

When CORS_ORIGINS=* the origin callback reflects any Origin, and if CORS_CREDENTIALS=true is also set, every website on the internet can make credentialed requests to your API. The env schema allows this combination in any NODE_ENV.

Fix: add a zod superRefine in env.ts: reject "*" when NODE_ENV=production, and reject "*" + CORS_CREDENTIALS=true everywhere. Two lines, closes the foot-gun permanently.

Medium Unknown routes bypass the unified envelope

src/lib/express.ts:70–71

There is no catch-all 404 handler. A request to an unmounted path falls through to Express's default handler, which returns an HTML Cannot GET /whatever page — breaking the "every endpoint returns one envelope" contract and leaking that the framework is Express.

Fix: before errorHandler, add app.use((req, _res, next) => next(new NotFoundError())).

Medium Cache wrap(): null results are never cached; no stampede protection

src/packages/cache/redis-cache.ts:37–44

get() returns null both for "key missing" and "cached value was null", so wrap("user:42", …, () => findById(42)) re-runs the producer on every call when the user doesn't exist — a cache that never caches misses (and a nice DoS lever on guessable IDs). Concurrent callers also all run the producer at once (dogpile). JSON.parse on a corrupt entry throws a raw 500.

Fix: store a sentinel wrapper ({v: value}) to distinguish miss from null; wrap JSON.parse in try/catch → treat as miss; consider a simple per-key in-flight promise map for stampedes.

Medium Numeric env vars validated as strings — PORT=abc boots to NaN

src/config/env.ts:22,34–36,55–58 · src/config/app.config.ts:99–160

PORT, REDIS_PORT, RATE_LIMIT_* etc. are z.string() and only parseInt-ed later in app.config.ts. Garbage passes validation and surfaces as NaN deep in the stack — the exact failure mode the fail-fast env layer exists to prevent. Similarly, JWT_EXPIRES_IN's regex accepts nonsense units like "1x".

Fix: use z.coerce.number().int().positive() in the schema and drop the scattered parseInt calls; validate expiry strings against ms() actually parsing them.

Medium Shutdown deadline (10s) contradicts the worker's PM2 kill window (30s)

src/lib/shutdown.ts:8 · ecosystem.config.cjs:53

PM2 gives bp-worker 30s to finish in-flight jobs, but shutdown.ts force-exits at a hard-coded 10s. Long jobs (a slow SMTP send, a batch task) get killed 20 seconds earlier than you budgeted, and BullMQ will re-run them — fine only if every job is idempotent.

Fix: make the timeout configurable per process (env or parameter) and align it just under each PM2 kill_timeout. And keep writing jobs to be idempotent regardless.

Note Docs drift + small nits

README.md · ecosystem.config.cjs · src/lib/security.ts

① README says web runs instances: max and worker runs fork mode; the actual config is instances: "1" and cluster — harmless today, misleading later. ② PEM keys live in env vars; the keys:jwt script handles newline escaping, but hand-editing .env.production will break keys silently — always regenerate via the script. ③ mongoSanitize can't scrub Express 5's read-only req.query (documented) — zod remains the real guard there; keep schemas .strict() where possible. ④ Mongoose autoIndex stays on in production — fine at small scale, disable + migrate indexes explicitly if collections grow.

06 Best practices when reusing this as your foundation

  • Copy packages/ verbatim, edit lib/. The repo's own layering rule is right: packages/acl, packages/mongoose, packages/cache are app-agnostic; policy lives in lib/. Keep that boundary sacred in new projects.
  • Never deploy with authenticate reading x-roles. Make replacing it step zero of every new project — consider deleting the placeholder body and throwing "not implemented" so it can't ship by accident.
  • Regenerate JWT keys per project, per environment. yarn keys:jwt --env production. Never share a key pair across projects; never commit env files (the gitignore already protects you — keep it that way).
  • Keep zod as the single trust boundary. mongoSanitize is defense-in-depth, not the guard. Every new route gets .validate(); prefer .strict() object schemas so unexpected keys are rejected, not ignored.
  • New feature = new module. Copy modules/users/, keep the folder-name-equals-module-name rule (i18n and model loading depend on it), and declare depends honestly — the topo-sort only protects you if you do.
  • All jobs idempotent. BullMQ retries (3 attempts configured) plus the shutdown-timeout mismatch mean any job can run twice. Design handlers so that's harmless.
  • Let PM2 own logs in cluster mode. LOG_TO_FILE=false under PM2 (already enforced in the ecosystem file) — two processes writing one rotating file corrupts rotation.
  • Check the boot banner and warnings on every deploy. This audit found a silent security downgrade sitting in plain sight in the logs. Treat any warn at startup as a broken build.
  • TLS at the proxy, HTTP inside. The app deliberately dropped HTTPS handling — always front it with nginx/Caddy/ALB doing TLS + HSTS, set TRUST_PROXY to the real hop count, and set CORS_ORIGINS to explicit origins.
  • Soft-delete is the default read model — remember the escape hatches. Admin screens and audits need .withDeleted(); uniqueness constraints must account for deleted rows still existing (partial indexes on is_deleted: false).
  • Run yarn npm audit before each reuse and bump majors consciously — Express 5, Mongoose 9, and Zod 4 are all recent majors whose ecosystems are still settling.
