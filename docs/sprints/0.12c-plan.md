# 0.12c — four fixes found upgrading an app from 0.10.1 to 0.12.0-rc.2

Status: **proposed** on 2026-10-14 against `2f4783d` (the `v0.12.0-rc.2`
tree; the merge after it changes no file). Nothing here is breaking. It can
ship as the next candidate (`0.12.0-rc.3`) or in `0.12.0` itself. Each
sprint item in §6 is committed on its own after its checks pass. This file
is the tracker and gains the evidence as items land.

## Context

k13 (`k13-blog-monorepo-v1/apps/api`, 19 modules, 158 routes, 65
environment variables) was carried from core 0.10.1 to 0.12.0-rc.2 with
`tulipes migrate 0.11` and `tulipes migrate 0.12`. That work is recorded in
k13's `docs/plan/phase-32-tulipes-0.12.md`. The migrations had defects of
their own, which belong in a separate plan. This one covers the four
problems that are **not** in the migrations: they affect an app that is
already on 0.12, every time it runs.

| # | Where | Problem | Severity |
|---|---|---|---|
| 1 | `@tulipes/cli` — `tulipes spec` | Crashes when the core module declares `publicDomain` as an environment value | High: the command is unusable for such an app |
| 2 | `@tulipes/core` — settings | A module whose own zod is 4.x cannot declare settings: TypeScript gives up | Medium: blocks a supported pattern; runtime is fine |
| 3 | reference app (what `tulipes init` copies) | The app cache opens lazily and fails fast, so the first requests after a boot miss it, and log a false outage | Medium: wrong behaviour on every boot; one possible security edge (§3.4) |
| 4 | `@tulipes/core` — banner | Two rows labelled "Settings" when a settings provider is declared | Low: cosmetic |

None of the four is caught today. The smoke scripts and test suites build
apps shaped like the reference app, which keeps `publicDomain` as a
setting, uses one zod copy, and never asserts on the first request after a
boot or on the banner's rows.

## 1. `tulipes spec` reads an environment value under inspection

### 1.1 Symptom

```
$ pnpm exec tulipes spec --openapi docs/openapi.json --postman docs/collection.json
config.core.publicDomain is an environment value, not available during inspection — read it inside a handler or a bootstrap, not while building routes
```

The process exits 2 and writes no document. `tulipes routes` on the same
app works.

### 1.2 Reproduction

1. Take the reference app (`example/`).
2. Remove `publicDomain` from `modules/core/module.config.ts`.
3. Declare it in `modules/core/package.json`:
   `"publicDomain": { "key": "PUBLIC_DOMAIN", "type": "string", "default": "localhost" }`.
4. `pnpm sync`, then `pnpm spec`.

### 1.3 Cause

`packages/cli/src/spec.ts:64`:

```ts
const url = options.url ?? defaultUrl(handle.ctx.config.server?.port, handle.ctx.config.core);
```

`defaultUrl` (`spec.ts:142`) evaluates `typeof core?.publicDomain`. Under
inspection, phase 6b binds every environment value as a getter that throws
(`packages/core/src/env/bind.ts`), so the read throws. That is the guard
working as designed. The CLI assumes `publicDomain` is a *setting*, because
the reference app makes it one. 0.12b made an environment value and a
setting indistinguishable at the call site, so the assumption no longer
holds.

### 1.4 Fix

Read the domain without tripping the guard, from the source that knows
which kind it is:

1. If `core` has an **own enumerable** `publicDomain`, it is a setting:
   use it as today. Settings are enumerable and environment values are
   not, so `Object.prototype.propertyIsEnumerable.call(core, "publicDomain")`
   decides this without invoking a getter.
2. Otherwise ask the inspector:
   `handle.ctx.settings.describeEnv("core").find((v) => v.name === "publicDomain")`.
   Under inspection the value is resolved leniently, and `describeEnv`
   returns a non-secret value. Use it when it is a non-empty string.
3. Otherwise `localhost` on the configured port, as today.

`defaultUrl` takes `handle.ctx`, not `config.core`, so it can do step 2.
No other CLI command reads a module's config under inspection (`grep -n
"config\.core" packages/cli/src/*.ts` finds only this line). `@tulipes/spec`
reads only `config.app`, which is app config and never an environment
value.

Rejected: catching the error and falling back to localhost. It would hide
the domain a deployment configured, and the document would advertise the
wrong server without saying so.

### 1.5 Tests

In `packages/cli/tests/cli.test.ts`, on a generated app (the fixtures
already scaffold one), run `runSpec`:

- **`publicDomain` as an environment value**, with
  `PUBLIC_DOMAIN=api.example.test`: the document's `servers[0].url` is
  `https://api.example.test`, and the exit code is 0.
- **The same declaration with no value set**: `http://localhost:<port>`.
- **`publicDomain` as a setting** (the reference app's shape): unchanged.
- **A secret named `publicDomain`**, an odd declaration but a legal one:
  `describeEnv` withholds the value, so the URL is localhost, never the
  secret.

Also add the environment-value variant to `scripts/scaffold-smoke.mjs`,
which today runs `spec` only on the reference shape.

### 1.6 Acceptance

`tulipes spec` succeeds on both declarations of `publicDomain`, and never
evaluates an environment-value getter. k13 can drop `--url
http://localhost:3000` from its `spec` script.

## 2. Settings cannot be declared with a module's own zod 4

### 2.1 Symptom

In a module whose `package.json` depends on `"zod": "^4.6.5"` (k13's `ai`
module does, for the AI SDK), a plain declaration fails to typecheck:

```
modules/ai/module.config.ts(10,16): error TS2589: Type instantiation is excessively deep and possibly infinite.
modules/ai/module.config.ts(11,11): error TS2589: Type instantiation is excessively deep and possibly infinite.
```

The two positions are `defineConfig(` and `z.object(`. Flat and nested
schemas fail alike. **At runtime the same declaration works.** k13 booted
with it on 0.11 and on 0.12, and the banner listed the namespace at v1. That
needs `instanceof z.ZodObject` (`define-config.ts:74`) and
`z.toJSONSchema` (`define-config.ts:94`) to accept a schema from the other
copy, and they do: both majors identify instances by trait, not by
prototype.

### 2.2 Cause

Core depends on `zod ^3.25` and imports `zod/v4` from it. `defineConfig`
and `ConfigDeclaration` constrain their parameter nominally:

```ts
export interface ConfigDeclaration<Schema extends z.ZodObject = z.ZodObject> { … }   // define-config.ts:26
export function defineConfig<Schema extends z.ZodObject>(…)                          // define-config.ts:41
```

A module with zod 4.6 hands it a `ZodObject` from a different package, whose
internal types (`$ZodTypeInternals` and friends) differ. TypeScript
compares the two structurally, recursively, and hits its depth limit. `tulipes sync` makes the same assumption when it writes
`import("zod/v4").output<…>` into `types/tulipes.d.ts`
(`packages/cli/src/sync.ts:86`). That specifier resolves from the app root,
not from the module.

Core already avoids this for route schemas. `packages/core/src/http/schema.ts`
types them structurally (`ValidatableSchema`: anything with `safeParse`),
"so core keeps no opinion about which zod major an app uses". Settings are
the one place that opinion survived.

### 2.3 Fix

Make settings declarations as structural as routes, at the type level only:

1. In `define-config.ts`, constrain `Schema` to a minimal structural
   interface instead of `z.ZodObject`: an object with `shape`,
   `safeParse`, and zod 4's `_zod` marker. Both zod 3.25's `zod/v4` and
   zod ≥ 4 satisfy it. The output type comes from `_zod.output`, which both
   expose, instead of `z.output<Schema>`.
2. Keep the runtime checks: `instanceof z.ZodObject`, `fieldMeta()`'s walk
   over `_zod.def`, and `z.toJSONSchema`. Add one test that pins
   cross-copy behaviour (§2.4), so a future zod release that breaks trait
   identity fails here, not in an app.
3. In `sync.ts`, emit the output type through the same `_zod.output`
   accessor instead of `import("zod/v4").output`, so the generated file no
   longer depends on which zod the app root resolves.
4. Document it in the core README's settings section: a module may use
   either zod major; `zod/v4` from 3.25 remains what the reference app
   uses.

Rejected:

- **A `zod` peer range of `^3.25 || ^4`.** It moves the problem: with two
  majors installed, the module and core can still resolve different copies.
- **Telling apps to import core's zod for settings** (a re-export).
  Possible today with a package alias. It works, but it puts a
  framework-internal rule into every module that uses zod 4.

### 2.4 Tests

- `packages/core/tests` gains a fixture module whose `package.json`
  depends on zod 4 (add `zod4` as `npm:zod@^4` to the workspace's
  devDependencies). Its `module.config.ts` declares a nested settings
  schema with zod 4. The test boots it, writes through `ctx.settings.set`,
  reads `ctx.config.<module>`, and calls `ctx.settings.describe()` (JSON
  Schema).
- `pnpm test:types` includes the same fixture's `module.config.ts` and its
  generated `types/tulipes.d.ts`, and must pass. **This is the regression
  test for TS2589.**

### 2.5 Acceptance

A module may declare settings with either zod. The typecheck, the boot,
`set`, `describe` and the generated types all work. k13 can move its AI
module's two ceilings back into `module.config.ts`.

## 3. The reference app's cache misses until Redis connects

### 3.1 Symptom

On every boot of a generated production app, the first requests find the
cache unavailable. Each one:

- misses (`get` resolves `null`);
- fails to store (`set` is swallowed);
- logs once per 30 s: `[cache] redis get failed; serving without cache:
  Stream isn't writeable and enableOfflineQueue options is false`.

That is a false outage message at every start, and `wrap()` stops being
read-through for the first few requests. In k13 this minted two analytics
salts for one day: the first two requests each computed and returned their
own. Its test caught it as soon as the file loaded.

### 3.2 Cause

`example/modules/core/helpers/cache/index.ts`, copied verbatim into every
app by `tulipes init` (`packages/cli/templates/app/...`):

- `appCache()` (`index.ts:20`) creates the ioredis client **on first use**.
- It uses `enableOfflineQueue: false` (`index.ts:30`), deliberately, so
  that a Redis outage costs a miss rather than a stalled request.

Combined, the first commands are sent while the client is still
connecting. ioredis rejects them at once, and `RedisCache` turns each
rejection into a miss and a warning. `bootstrap/cache.bootstrap.ts` exists
but only returns `closeCache`.

### 3.3 Fix

Open the cache at boot and wait, bounded, for it to be ready. Keep the
fail-fast behaviour for real outages afterwards.

1. `helpers/cache/index.ts` gains
   `openCache(ctx, timeoutMs = 5000): Promise<void>`. It calls `appCache(ctx)`
   and, if the Redis client is not yet `ready`, waits for its `ready`
   event or the timeout, whichever comes first. It never throws. A Redis
   that does not come up in time leaves the app as it is today: missing,
   and saying so.
2. `bootstrap/cache.bootstrap.ts` calls it in every mode except inspection,
   where bootstrap does not run anyway, and returns `closeCache` as now.
   Bootstrap runs before routes and queues, so the first request and the
   first job both find the cache ready.
3. The same change in the minimal template if it carries the cache. It
   does not today; check when implementing.

k13 applied exactly this (`apps/api/modules/core/helpers/cache/index.ts`,
`openCache`) and its analytics test passes.

### 3.4 A consequence to verify before release

The auth module caches resolved sessions in this cache and deletes the
entry on every revocation path (`forgetUser`, `example/modules/auth/helpers/session-cache.ts`).
With several replicas sharing Redis, consider a replica that boots while
another is serving:

1. Replica B is connected and caches session S.
2. Replica A has just booted, receives a revocation for S, and calls
   `del`.
3. A's client is still connecting, so `del` is rejected and swallowed.
4. B keeps resolving S from the cache until the entry expires
   (`auth.cacheTtlSeconds`, at most `accessTtl`).

This is reasoning from the code, **not reproduced**. If it holds, the fix
above narrows the window to the bootstrap's wait. A revocation that cannot
reach the cache should probably also fail loudly, or retry, rather than be
swallowed. Decide that with the security model (`docs/security-model.md`
already discusses the cache bound).

### 3.5 Tests

In the reference app's suite (`example/modules/core/tests/core.test.ts`):

- **After boot, the cache is ready.** The module's Redis client is `ready`
  before the first request, and `wrap(key, ttl, f)` called twice in a row
  through two requests runs `f` once.
- **No cache warning at startup.** Capture `console.error` across the boot
  and the first request: no `[cache] redis` line.
- **Redis absent:** the boot still completes after the bounded wait, and
  requests are served, as today. Use an unreachable `REDIS_URL` with the
  queues provider off.

If §3.4 is confirmed, add a test in the auth suite: a revocation issued by
a fresh boot reaches the shared cache.

### 3.6 Acceptance

A fresh boot logs no cache failure, and the first request is a cache hit
when it should be. A boot without Redis behaves as today, after at most the
timeout.

## 4. Two "Settings" rows in the banner

### 4.1 Symptom

With `"settings": "@tulipes/mongoose/settings"` declared:

```
➜  Settings   mongodb://127.0.0.1:27018/k13.settings (poll)  ● ready  ·  mongoose-settings
➜  Settings   mongodb://127.0.0.1:27018/k13.settings (poll)  ·  core v1, security v1, auth v1, …
```

### 4.2 Cause

`packages/core/src/boot/banner.ts`:

- line 49: the providers loop prints a row per acquired provider, and
  `settings` is one of them since 0.11;
- lines 63–69: a second row is pushed unconditionally for the
  namespaces. It is also labelled "Settings", and repeats the store's
  label.

### 4.3 Fix

One row. When a `settings` provider is among `handle.providers`, append
`·  core v1, security v1, …` to that provider's row and push nothing else.
Otherwise, for core's file store, keep today's second row, which is then
the only one. "no module declares settings" stays as the namespace text in
whichever row is printed.

### 4.4 Tests

The banner is printed by `printStartupBanner`. Add a unit test that calls
it with a stubbed handle, or capture stdout around a boot in
`settings.test.ts`, and assert exactly one row starting with `Settings`:

- with a settings provider;
- with the file store;
- with no namespace declared.

### 4.5 Acceptance

One "Settings" row in every configuration.
