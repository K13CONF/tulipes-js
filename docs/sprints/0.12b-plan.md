# 0.12b — one config: environment values in `ctx.config`, no `Environment`

Status: **in progress** (see §11), proposed on 2026-10-13 against `cc0cf25`
(0.12-S06), with the owner's decisions recorded in the context section.
Ships in the 0.12 line as its next candidate (0.12.0-rc.2), so an app on
0.11 runs one migration, `tulipes migrate 0.12`, which gains these steps. Each sprint item in §8 is committed on its own after its
checks pass; this file is the tracker and gains the evidence as items land.

## Context

An app reads values from three places today:

| Source | Declared in | Read with | Live? |
|---|---|---|---|
| Settings | `module.config.ts` (zod) | `ctx.config.<module>.<field>` | yes, editable |
| App config | `config/app.config.ts` | `ctx.config.<key>` | no |
| Environment | `package.json` `tulipes.env` (array) | `ctx.Environment.get("NAME")` | no |

The environment is a separate API with its own store (`VariableStore`), its
own typing target (`KnownVariables`) and its own vocabulary (UPPER_SNAKE
names), so a module reaches the same kind of value two different ways.

Decisions taken with the owner (2026-10-13):

- **`Environment` is removed**: the class, `ctx.Environment`,
  `BootHandle.env`, `VariableStore`, `KnownVariables`. The resolver that reads
  `.envs/.env.<APP_ENV>` and `process.env` stays, as an internal of boot.
- **A module's environment values land in its own config namespace**:
  `modules/core` declaring `port` is read as `ctx.config.core.port`, beside
  core's settings. They're read-only, never persisted, and never serialised (§3).
- **`tulipes.env` becomes an object keyed by the config name**, with `key`
  naming the variable in the env file:

  ```jsonc
  "env": {
    "port":       { "key": "PORT", "type": "number", "group": "http", "default": 3000,
                    "description": "HTTP port the backend process listens on" },
    "mongodbUri": { "key": "MONGO_URI", "type": "url", "group": "database", "description": "..." }
  }
  ```
- **Core and providers read fixed app-config keys**, which
  `config/app.config.ts` fills from the environment values it now receives:
  `server.port` (core), `mongoose.{uri,user,pass,dbName}`
  (`@tulipes/mongoose`), `bullmq.redisUrl` (`@tulipes/bullmq`). No framework
  code reads a variable by name any more.
- **MongoDB is configured by parts plus an optional full URI**: username,
  password, host, database name, and `mongodb_uri`, which wins when it is set.
  A replica set, `mongodb+srv://` or connection options need the full URI.

Decided in this plan (flagged for review):

- Every field of today's spec survives except `name`: `key`, `type`
  (`string | number | boolean | enum | url | secret`), `description`,
  `group`, `enum`, `required`, `default`, with the same coercion and
  `required` ⊕ `default` rule. The owner's sample used `"type": "string"`
  for a password; the reference app uses `secret` for it, which is what
  keeps a password out of `GET /config` and `env:check` output.
- A config key is camelCase, `^[a-z][a-zA-Z0-9]*$`, like a settings field
  (owner's decision: the two share a namespace, so they share a style).
  `tulipes migrate 0.12` derives it from the variable name
  (`MONGO_URI` → `mongoUri`).
- `key` stays UPPER_SNAKE and unique across the app. Each env file and
  container variable still has exactly one owner.
- `APP_ENV` stays a process selector, not a module variable. It is read as
  `ctx.appEnv`, together with `ctx.mode`.
- Breaking for every app, but 0.12.0-rc.1 is not tagged, so it ships as
  **0.12.0-rc.2** (owner's decision) and `tulipes migrate 0.12` carries it.
- `tulipes env:check` stays as it is named (owner's decision).
- Code style, from the owner: every new module reads as prose for a human,
  with a comment wherever the *why* is not in the code, and each unit has one
  reason to change — the resolver reads files, the binder shapes
  `ctx.config`, the describer reports; none knows the others' internals.
- **Deployments keep working.** Env-file and container variable names are
  unchanged, because `key` preserves them. A 0.12 app's `MONGO_URI` still
  works, as the full-URI override.

## 1. The declaration

`packages/core/src/env/spec.ts`: `envFileSchema` becomes
`z.record(configKey, variableSpec)`, and `variableSpec` gains `key` and loses
`name`. A module may declare nothing (`env` absent or `{}`).

An array is refused with the message `tulipes.env is an object keyed by
config name since 0.12 — run tulipes migrate 0.12`, the same pattern as the
0.11 `meta.variables.json` refusal. `modules/manifest.ts` validates the same
schema, so both checks change together. Today they disagree in name only.

Boot rejects:
- a duplicate `key` across modules (one owner per variable)
- a config key that is also one of the module's settings fields
- a config key named like a Tulipes-reserved one: `then`, or anything
  starting with `__`

## 2. The boot pipeline, phase by phase

| Phase | Today | 0.12b |
|---|---|---|
| 1 environment | `Environment.load` → `ctx.Environment` | `resolveEnv(rootDir, appEnv)` → `EnvValues` (`{ [module]: { [key]: value } }`) and `EnvDescription` (owner, key, type, source, isSet, secret), kept by boot, not on ctx. Same precedence: `process.env` › `.envs/.env.<APP_ENV>` › `default`. `NODE_ENV` mirroring unchanged. `ctx.appEnv` set. |
| 1 (inspect) | declarations validated, every `get()` throws | declarations validated, **no value read**. `EnvValues` holds placeholders (`default`, else `""` / `0` / `false` / the first enum entry) for phase 4 only. |
| 2–3 graph, exploration | — | unchanged |
| 4 declarations | `appConfig(Environment)` | `appConfig(env, { appEnv, mode })`: `env` is a frozen copy of `EnvValues`. It returns the seed, including `server`, `mongoose` and `bullmq`. Refused if it returns a top-level key equal to a module name, since that slot belongs to the module. |
| 5 providers acquire | mongoose reads `MONGO_URI` via `Environment` | mongoose reads `ctx.config.mongoose` and passes `createConnection(uri, { user, pass, dbName })`, so nothing is URL-encoded by hand. A missing `uri` is the same providers-scope error, naming `config.mongoose.uri`. mongoose-settings likewise. |
| 6 settings | `ctx.config[ns] = { ...values }` | unchanged, then **6b** (new): for every module with env values, define each key on `ctx.config[module]` (created if the module has no settings) as a **non-enumerable, non-writable getter**. |
| 7 i18n, time zones | `env.appEnv` | `ctx.appEnv` |
| 8 ACL, agent | — | unchanged |
| 9 bootstrap | modules read `ctx.Environment` | modules read `ctx.config.<module>.<key>` |
| 10 queues, sockets | bullmq reads `REDIS_URL` | bullmq reads `ctx.config.bullmq.redisUrl` |
| 11 backend | port from `PORT` if declared, else 3000; `errorHandler(env.appEnv)` | port = `BootOptions.port` › `ctx.config.server.port` › 3000. `errorHandler(ctx.appEnv)`. Raw-response warning on `ctx.appEnv === "development"`. |
| 12 banner | `env.appEnv` | `ctx.appEnv` |
| shutdown | — | unchanged |

Why 6b defines **getters**:

1. **Settings writes keep them.** A local or remote write goes through
   `Object.assign(target, applied)` on the same object, so the getters
   survive. Phase 6 replaces the object only before 6b runs, never after.
2. **Inspection keeps today's guarantee.** Under inspection the getter
   throws `config.core.port is an environment value, not available during
   inspection — read it inside a handler or a bootstrap`, which is exactly
   today's message for `Environment.get` while building routes.
3. **Nothing serialises them.** Non-enumerable keys are skipped by `{ ...x }`,
   `JSON.stringify`, `Object.keys` and `console.log`'s default view. So
   `ctx.settings.describe()` (which spreads the namespace) and any
   `res.json(ctx.config.auth)` cannot leak a secret, and the settings store
   never persists one. A test pins each of these (§7).
4. **They are read-only.** Assigning to one throws in strict mode (ESM is
   strict), the same as writing an undeclared variable throws today.

Cost: `console.log(ctx.config.core)` doesn't show the env values. The README
and the env skill guide say so, and `tulipes env:check` is the place to see
them.

## 3. Core API (`packages/core`)

- **Removed:**
  - `Environment`, `EnvironmentOptions`, `VariableStore`, `DescribedVariable`
    and `KnownVariables`
  - `metaFileSchema`, `MetaFile`, `LEGACY_META_FILENAME` (the
    meta.variables.json refusal moves into the modules phase's root hints,
    where it already lives)
  - `Ctx.Environment` and `BootHandle.env`
  - the `"./env"` export, and the `export * from "./env"` in `src/index.ts`
- **Moved:** `appEnvs` and `AppEnv` go to `@tulipes/core/boot` (used by
  testing, the error handler, i18n, the settings file name and the banner).
- **Added:**
  - `Ctx.appEnv: AppEnv` and `BootOptions.port?: number`
  - `AppConfigFn = (env: EnvValues, meta: { appEnv: AppEnv; mode: ProcessMode }) => ...`
    - `EnvValues` is an interface in `@tulipes/core/config`, augmented by
      `tulipes sync` (§5), and is the codegen target that replaces
      `KnownVariables`
  - `ctx.settings.describeEnv(module)`: the env metadata the console needs
    (key, env `key`, type, description, group, required, enum, default,
    source, is_set, is_secret, and value for non-secrets). It's on
    `settings` because that is already the "inspect and write" side of
    `ctx.config`.
  - `GlobalConfig` gains `server?: { port?: number }`. The providers augment
    `mongoose?` and `bullmq?` from their own packages.
- **Kept as internals** (no longer exported): `coerceValue`,
  `variableSpecSchema`, `discoverModuleMeta`. The CLI's `sync` and `env:check`
  need them, so they're exposed under `@tulipes/core/boot` as
  `readEnvDeclarations()` and `resolveEnv()`, marked internal, the way
  `Settings` is.
- `BootScope` keeps `"env"`.

## 4. Providers

- `@tulipes/mongoose`: `database.ts` and `settings-provider.ts` read
  `ctx.config.mongoose` (`uri` required; `user`, `pass`, `dbName` optional,
  passed as driver options). An augmentation types `GlobalConfig.mongoose`.
  The tests move from `tulipes.env` arrays plus `stubEnv(MONGO_URI)` to a
  fixture `app.config.js`.
- `@tulipes/bullmq`: `load-queues.ts` reads `ctx.config.bullmq.redisUrl`.
  An augmentation types it. Tests change the same way.
- `@tulipes/socket.io`, `@tulipes/mcp`: no change in code. Their peer ranges
  move with core.
- `@tulipes/testing`:
  - `appEnv` type from `@tulipes/core/boot`
  - `useTestApp` passes `port: 0` through `BootOptions.port` instead of
    relying on a declared `PORT`
  - `options.env` still sets `process.env` (an app's variables are still
    read from there)

## 5. CLI (`packages/cli`)

- `sync`:
  - generates `interface EnvValues { core: { port: number; ... } }` in
    `declare module "@tulipes/core/config"`
  - adds each module's env keys to that module's `GlobalConfig` property as
    `readonly`, merged with its settings type
  - `.env.example` is generated from `key`, grouped as today
- `env:check`:
  - resolves through `resolveEnv`
  - prints `config.<module>.<key> ← KEY=value`, with secrets redacted
  - exits 1 with the same aggregate report
- `spec`: `defaultUrl` reads `config.server.port` and `config.core.publicDomain`.
  The `PUBLIC_DOMAIN` fallback goes, because nothing declares it.
- `new module`: no `env` key, as today. Its guidance text names `ctx.config`.
- `init`: next-steps text unchanged, since `.envs` names are unchanged.
- `config:import` (the 0.11 importer) has its own reader. It is left as it is,
  and its `MONGO_URI` read is documented as reading the env file.
- `migrate 0.12`, extended (§6).

## 6. Migration — `tulipes migrate 0.12`, extended

The existing command gains these steps, stays idempotent, and records the
key map and TODOs in `config/migration-0.12.json` beside the id map.

1. **`tulipes.env` array → object.** The config key is the camelCase of
   the name (`MONGO_URI` → `mongoUri`, `JWT_ACCESS_SECRET` →
   `jwtAccessSecret`), and `name` becomes `key`.
2. **Literal reads.** Inside module code, these rewrite to
   `ctx.config.<owner>.<key>`, using the destructured name where the file
   destructures `Environment`:
   - `Environment.get("X")`
   - `ctx.Environment.get("X")`
   - `env.store.get("X")`

   `…store.has("X")` becomes `ctx.config.<owner>.<key> !== undefined`, and
   `Environment.appEnv` becomes `ctx.appEnv`.
3. **Reported as TODOs, never guessed:**
   - a dynamic name (`get(name)`)
   - an `Environment` passed as a value (`logger(ctx.Environment, mode)`,
     `appCache(environment)`)
   - `store.set`
   - `describe()` / `snapshot()`
4. **`config/app.config.ts`:** the default export gains `(env, { appEnv })`.
   When the app declared `PORT` / `MONGO_URI` / `REDIS_URL`, it adds
   `server: { port: env.<owner>.port }`,
   `mongoose: { uri: env.<owner>.mongoUri }` and
   `bullmq: { redisUrl: env.<owner>.redisUrl }`. If the function isn't the
   plain `(() => ({ … }))` shape, that's a TODO.
5. `.envs/*` and deployment variables are untouched.

`scripts/upgrade-smoke.mjs` runs `migrate 0.12` on the published 0.11
starter, as today. It expects 0 TODOs from the reference app's literal
reads, and the factory TODOs listed in the report. It then typechecks and
boots to "database connection failed".

- **Call sites** (~25, from the 2026-10-13 sweep):

    `store.has("REDIS_URL")` becomes `ctx.config.core.redisUrl !== undefined`.

    env `key` so operators see `JWT_ACCESS_SECRET`. `seed-admin`,
    `tokens.secret()` and `passport` read `ctx.config.auth.*`.
  - **Security:** `rate-limit` reads `ctx.config.core.redisUrl` and
    `ctx.appEnv`.
  - **Log streams:** the per-boot `WeakMap<Environment>` becomes
    `WeakMap<Ctx>`.
  - **Settings controller:** reads `logFile` / `logDir`.
  - **Config console:** `describe.ts` reads `ctx.settings.describeEnv(name)`,

  - **Queues and scripts:** the queues in users and hello, `deploy-nginx.ts`
