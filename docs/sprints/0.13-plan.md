# 0.13 — an MCP process, credentials with scopes

Status: proposal, prepared on 2026-10-14 against `ed410c1` (0.12.0). Nothing
is implemented. 0.12 is the stable line (scoped RAI ids, environment values
in `ctx.config`, time zones); this is the plan for the line that gives the
agent surface a front door of its own.

**A word on "scope".** Since 0.12 a RAI id is `module:scope:resource[:extra]`,
and *scope* names its second segment (`bo`, `web`, `mobile`). The scopes this
plan adds belong to a **credential**: the grant patterns it is limited to.
The two meet naturally — `users:web:*` is a credential scope covering one
RAI scope of one module — but the credential's list is only ever called
`scopes` as a field of `Auth` or of a token, and the refusal code is
`OUT_OF_SCOPE`.

The brief it answers, in the maintainer's words: an *MCP mode* for the app,
where the developer configures the authentication method for it and
everything about it, and can specify **scopes** so a credential given to an
agent reaches less than the user who issued it.

Section 1 reviews the brief against the code as it is after 0.12. Sections 2
to 4 are the design. Section 5 is the sprint breakdown with acceptance
criteria, section 6 the migration, section 7 the evidence expected, section 8
the decisions taken and open, section 9 the backlog.

## 1. The brief, reviewed

| Idea | Verdict | Why, from the code |
|---|---|---|
| The app runs as an MCP server itself | **Yes, as a process entry in `@tulipes/mcp`, not a core mode.** `mcp.ts` beside `app.ts` and `worker.ts`; it boots the app with `boot({ mode: "script" })` and serves `ctx.agent` over MCP. | Since 0.11-S10 every tool is an action and `ctx.agent.invoke(name, input, actor)` takes an explicit actor, so an in-process server needs no request and no middleware — the problem S04 could not solve with route tools is gone. A fourth `ctx.mode` is not needed until a module has to branch on it (§8). |
| The developer configures the authentication method | **Yes: one declared function.** `config/mcp.config.ts` exports `defineMcp({ transport, identify })`; `identify(ctx, credential)` returns the actor or `null`. | The server has one question — who is calling — and the app is the only place with the answer. Two things the brief does not say that decide whether this is safe:

- An MCP process has the database and whatever role `identify` grants. The
  convenience path — a role from an environment variable — must be
  impossible in production and visible in the banner (§2.6).
- A scope is only useful if an agent's tool list reflects it. The manifest
  must filter by the actor, not the role (§2.3), or the model keeps choosing
  tools it will be refused.

## 2. Design

### 2.1 The MCP process

```ts
// mcp.ts — scaffolded beside app.ts and worker.ts
import { serveMcp } from "@tulipes/mcp";

await serveMcp({ rootDir: import.meta.dirname });
```

`serveMcp` boots the app (`boot({ mode: "script", handleSignals: false })`),
reads `config/mcp.config.ts`, opens the declared transport, and serves:

- `tools/list` → `ctx.agent.manifest(actor)` for the connection's actor.
- `tools/call` → `ctx.agent.invoke(name, input, actor)`; an `HttpError` from
  the gate (401, 403, 422, 404) becomes a tool error carrying the envelope's
  message, as the bridge does today; anything else is a tool error with the
  message and a logged stack.
- `instructions` from the module summaries, as today.

Shutdown is the app's: SIGTERM runs the cleanups, the transport closes first
(`ctx.signal`). The banner prints `mcp mode · stdio` or `· http :port`, the
identity source, and the actor when it is fixed for the process.

The `tulipes-mcp` bridge (HTTP door → stdio) stays for apps that do not want
a second process on the host; it gains nothing in this line and is the first
thing to delete if nobody uses it by 0.14.

### 2.2 `defineMcp`: transport and identity

```ts
// config/mcp.config.ts
import { defineMcp } from "@tulipes/mcp";
import { identifyCredential } from "@tulipes-example/auth";

export default defineMcp({
  // "stdio" (default) or { http: { port, path? } }
  transport: "stdio",
  // Who is calling. Null is a guest. Called once per stdio process, once per
  // HTTP request (cached by the auth module as sessions are).
  identify: (ctx, credential) => identifyCredential(ctx, credential),
});
```

`credential` is a string or `undefined`: for stdio, `--token` or
`TULIPES_MCP_TOKEN` at launch; for HTTP, the bearer of each request. The
return type is `ToolActor` (`Auth` plus `role`, now plus `scopes`). The file
is read by `@tulipes/mcp`, never by core; `tulipes routes` and `spec` do not
load it.

Rules enforced by `serveMcp`:

- No `identify` → every caller is a guest. Allowed: a guest manifest is
  exactly what the ACL grants `guest`.
- `identify` is the only way an actor gets a role. There is no `--as <role>`
  flag; the minimal preset's development identity is still an `identify`
  function (§2.6), so the rule has no exception to reason about.
- A transport the SDK does not know, or `http` without a port, is a boot
  error naming the file.

### 2.3 Scopes

A scope is a grant pattern in the ACL's grammar: an exact id, a prefix
wildcard (`hello:web:*`), or `*`. A credential carries a list of them; an actor
carries the list of its credential, or nothing when the credential has no
scopes (a password session, the seeded admin, a token issued without any).

```ts
// core: packages/core/src/http/index.ts
export interface Auth {
  isAuthenticated: boolean;
  user: AuthUser | null;
  session: AuthSession | null;
  /** Grant patterns this credential is limited to; absent means the role's full grant. */
  scopes?: readonly string[];
}
```

The rule, applied in both gates: **allowed = acl.can(role, permission) &&
(scopes === undefined || scopes cover permission)**, where "cover" is the
same `grantsCovering(permission).some(scope ∈ scopes)` the ACL uses. A scope
the role does not hold grants nothing; a scope list of `[]` reaches nothing.

- `rai()`'s gate reads `req.auth.scopes` next to `roleOf(req)`; a scoped
  request refused by scope answers 403 with code `OUT_OF_SCOPE`, distinct
  from `FORBIDDEN`, so an agent's refusal says which it was.
- `AgentRegistry.manifest(actor)` and `tools(actor)` accept an actor as well
  as a role (`string | ToolActor`); with an actor they filter by both. The
  HTTP door and the MCP process pass the actor.
- A custom `setAccessChecker()` replaces the whole decision, scopes included,
  as it replaces the ACL today; the manifest reports `authorization:
  "dynamic"` as before.

Scopes are never trusted from the client: they are read from the stored
credential at resolution time, like the role is read from the user.

### 2.4 API tokens in the auth module

A new model, `ApiToken`, in `modules/auth/models/api-token.model.ts`:

| field | |
|---|---|
| `token_id` | public id, `tok_` + 16 url-safe chars, indexed |
| `user` | the owner |
| `name` | what the user called it ("claude-code laptop") |
| `secret_hash` | SHA-256 of the secret; the secret is shown once at creation |
| `scopes` | `string[]`, validated as grant patterns at creation |
| `expires_at` | optional; a TTL index removes the row |
| `last_used_at` | touched at most once a minute, as sessions are |
| `revoked_at` | set by the owner or by `revokeAccess()` on the user |

The bearer is `tul_<token_id>_<secret>`; the prefix is what lets the request
pipeline tell it from a JWT without decoding. Resolution: look up
`token_id`, compare the hash in constant time, refuse if revoked or expired,
load the user (the role comes from the user, never from the token), cache
the resolved actor under the token id with the session cache's TTL and
forget it on revocation — the same shape as S08b. Endpoints, all under
`auth:web:tokens`, granted to `user` and above:

- `POST /auth/tokens` `{ name, scopes?, expires_in? }` → `{ token_id, name,
  scopes, expires_at, secret }`, the secret only here, ever.
- `GET /auth/tokens` → the user's tokens without secrets.
- `DELETE /auth/tokens/:token_id` → revoke; 404 for another user's.

A token may name scopes its role does not hold — they grant nothing, and
the intersection is computed at use so a role change applies at once. The
console (`tulipes-permissions` skill) documents the pattern: issue the
narrowest scope the task needs; `hello:web:*` for an agent that greets.

`identifyCredential(ctx, credential)` in `modules/auth/lib/index.ts`
resolves either kind — an API token by prefix, otherwise an access JWT
through the existing path — and is what both the request pipeline and
`config/mcp.config.ts` call. One resolver, two front doors.

### 2.5 Transports

- **stdio.** `node mcp.ts --token tul_…` or `TULIPES_MCP_TOKEN`. One actor
  for the process, identified once; a revoked token is noticed on the next
  call because `invoke()` re-reads the cached actor, which revocation
  forgot. For Claude Code: `claude mcp add my-app -- pnpm mcp --token "$TOKEN"`.
- **Streamable HTTP.** `transport: { http: { port: 3100, path: "/mcp" } }`.
  The SDK's transport on node's `http`, one session per client as the
  specification defines, the bearer identified per request through the
  cache. No CORS, no cookies: a machine endpoint. The nginx template gains
  a commented `location /mcp` block so an operator can expose it behind the
  same ingress; `ingress-smoke.mjs` does not need to change.
- **Not in this line:** OAuth 2.1 (authorization server, dynamic client
  registration, PKCE) for public HTTP servers, SSE's legacy transport.

### 2.6 Safety rules

- `identify` returning a role **from configuration rather than from a
  credential** is development only. The minimal preset's `mcp.config.ts`
  reads `MCP_ROLE` and `serveMcp` refuses it when `APP_ENV` is
  `production` or `staging` with the reason; the production preset never
  ships such a function.
- Every `tools/call` writes one audit line through the core logger: actor
  id (or `guest`), token id when there is one, tool name, outcome (ok /
  refused with code / failed), duration. Inputs are never logged.
- An API token cannot create API tokens (`auth:web:tokens` is excluded from any
  scope by the issuer; `*` on a token still does not cover it). Otherwise a
  leaked token mints its own successors.
- `revokeAccess(user)` and password changes revoke the user's API tokens as
  they end sessions today.
- The HTTP transport refuses to bind without `identify` in production: an
  open guest MCP endpoint on the network is a decision, not a default.

### 2.7 Generated apps

Both presets gain `mcp.ts`, a `"mcp": "node mcp.ts"` script, and
`config/mcp.config.ts`. The production preset's auth module gains the model,
the three endpoints, `identifyCredential`, the pipeline change and the
revocation hooks, with tests in `modules/auth/tests/`. The minimal preset's
`mcp.config.ts` is the development identity. The `tulipes-agent-tool` and
`tulipes-permissions` skills document tokens and scopes; AGENTS.md's rule 14
gains one sentence on scopes. The `agent` module's HTTP door passes the
actor to `manifest()` so a scoped token sees a scoped list there too.

### 2.8 Why not a core `mcp` mode

`processModes` is `backend | worker | script`, and the fork decides what
starts after bootstrap. An `mcp` entry would need core to know a transport
it must not depend on, or a provider seam for "the thing that serves after
boot", which is what script mode already is from the caller's side. If a
module one day needs `ctx.mode === "mcp"` (a seed to skip, a queue not to
register), the mode is added then with the reason recorded; until then the
banner says what the process is.

## 3. Rejected alternatives

- **Scopes as a separate grammar** (OAuth-style `read:users`): a second
  vocabulary to keep in sync with the ACL's, and a translation nobody wants
  to maintain. The ACL's patterns are already what the console and `tulipes roles` show.
- **Scopes inside the JWT:** roles are deliberately not in tokens (a stale
  signed claim is a privilege bug waiting to happen, `helpers/tokens.ts`);
  scopes in a signed token would have the same problem, and sessions are
  not what agents should hold anyway.
- **Scopes enforced only in the MCP process:** a token that is narrowed over
  MCP but full over HTTP is not narrowed.
- **A role per agent** (`agent-reader` with its own grants): roles are app
  vocabulary, defined by modules; credentials are per user. A scoped token
  is a user acting with less, which is what an agent is.
- **OAuth first:** the right answer for a public MCP server and the wrong
  first step for an app serving its own agents; it needs an authorization
  server the preset does not have.

## 4. What stays exactly as it is

The agent surface (S10): `defineAgent({ summary, actions })`, `invoke()`'s
order (ACL, schema, handler), tool naming, the manifest shape apart from
filtering by actor. The HTTP door. The ACL grammar and `module.acl.ts`.
Sessions and the JWT pair. The settings store, the config console.

### 0.13-S02 — API tokens in the auth module (medium)

Status: implemented on 2026-10-15, after S03.1–S03.2. Decision 7 taken:
the prefix is the app's name (`config.app.name`, scope stripped), and
resolution reads only the id and the secret, so renaming the app does not
retire tokens. Departures from §2.4, each smaller than the plan:

- Revoking deletes the row (as ending a session does); there is no
  `revoked_at`.
- Tokens carry the password's `credential_version`, like sessions, so a
  password change retires them with no hook of its own; `forgetUser()`
  forgets their cached identities with the sessions', which covers role
  changes and deletion through the existing callers.
- "A token cannot issue tokens" is enforced by requiring a session to
  issue (a token resolves with `session: null`), not by excluding
  `auth:web:tokens` from scopes.
- Ids are `auth:web:tokens` (list), `auth:web:tokens:issue`,
  `auth:web:tokens:revoke`, granted to `user` as `auth:web:tokens:*`, the
  sessions pattern. Expiry is `expires_in_days` (1–365).

Local evidence (macOS, Node 24.14.0, MongoDB 7, Redis): the reference
app's typecheck and suite (8 files, 48 passed) with two new auth tests —
issue with the secret once and only a hash stored, a `hello:web:*` token
reaching `/hello/secret` (200) and refused `/users` (403 `OUT_OF_SCOPE`)
although the role holds it, listing without the secret, another user's
DELETE 404, revoke then 401; a token refused to issue tokens
(`TOKEN_NEEDS_SESSION`), invalid scope and expiry 422, an expired token
401, a forged secret 401, every token retired by a password change.
`tulipes routes` lists the three endpoints with `admin, sysadmin, user`.
Manually: a token issued over HTTP to the admin with `hello:web:*` and
given to `pnpm mcp --token` lists only `hello_web_greetings`.

Found on the way: the replica test in `auth.test.ts` configures passport
(a process-wide singleton) from a second boot and shuts it down, so any
test after it resolves bearers against a closed context. It is kept last,
with a comment; making passport per-app is backlog.

- S02.1 `ApiToken` model, `tul_` bearer format, hashing, expiry, the cache.
- S02.2 `POST`/`GET`/`DELETE /auth/tokens`, `auth:web:tokens` granted to `user`
  and above; a token cannot cover `auth:web:tokens`.
- S02.3 `identifyCredential()` in the auth lib; the request pipeline resolves
  `tul_` bearers through it; `revokeAccess()` and password changes revoke

- S02.4 Tests in `modules/auth/tests/`: issue, use over HTTP with scopes,

## 6. Migration for an app on 0.12

Additive; nothing breaks. For the MCP process:

1. `pnpm add -D @tulipes/mcp` (if the bridge was not already there), copy
   `mcp.ts` and `config/mcp.config.ts` from the reference app, add the
   `mcp` script.

## 8. Decisions

Taken on 2026-10-14:

1. The MCP process is an entry in `@tulipes/mcp` over script mode, not a
   core mode (§2.8).
2. Identity is `defineMcp({ identify })`, the only way an actor gets a role
   in the MCP process; no `--as` flag (§2.2).
3. Scopes are ACL grant patterns, checked in core's two gates after the
   role, never widening it (§2.3).
4. The agent credential is an API token in the auth module, hashed, named,
   revocable, scoped; roles come from the user (§2.4).
5. Two transports: stdio and Streamable HTTP with bearer; OAuth is backlog
   (§2.5).
6. A configured role is development only and refused in production (§2.6).

Still open:

7. ~~`tul_` or the app's name~~ — taken 2026-10-15: the app's name (S02).
8. ~~The app's port or its own~~ — taken 2026-10-15: its own port (S03.3);
   one more ingress rule, and the MCP process stays separable.
9. Whether `last_used_at` and the audit line are enough, or a token needs a
   per-token call counter the owner can see in `GET /auth/tokens`.
