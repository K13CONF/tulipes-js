# 0.11 — settings in the database, three-file modules, an agent surface

Status: proposal, prepared on 2026-10-07 against `9c102cd` (0.10.1), revised
the same day after maintainer review (lifecycle hooks removed, `settings`
reduced to the log stream, section 9 added). Nothing here is implemented.
0.10 is the stable line whose contracts are settled; this is the plan for
the breaking line that README, `docs/support.md` and the changelog all defer
to.

The brief it answers, in the maintainer's words: configuration lives in the
database through a sys `config` module, each module declares its own config
schema, a module folder holds only `module.config`, `module.acl` and
`package.json` with everything else in a dedicated folder, the framework is
for APIs only, and every module carries an `ai-agent` folder describing the
tools and actions it offers. The goal is a next version that is simpler,
friendlier to developers and friendlier to coding agents.

Section 1 reviews each idea against the code as it is. Sections 2 to 5 are
the design that follows. Section 6 is the sprint breakdown with acceptance
criteria, section 7 the migration, section 8 the decisions taken and still
open, section 9 the performance and developer-experience cards that are
candidates for the line but not yet scheduled.

## 1. The proposal, reviewed

| Idea | Verdict | Why, from the code |
|---|---|---|
| Config in the database, by default | **Yes, with a split.** Two layers: an *environment* of a dozen variables the process needs before a database answers, and *settings*, everything else, stored and editable at runtime. | Today the production preset declares 32 variables in six `meta.variables.json` files, and a change to any of them needs an `.env` edit plus a PM2 restart (`settings` module, S08a/S08i). Most are policy, not deployment facts: `USERS_SIGNUP_MODE`, `HELLO_GREETING`, every rate limit, CORS, HSTS. Only connection strings, the port, the log destination and secrets are genuinely process-level. |
| Everything in the database except database credentials and `APP_ENV` | **No: secrets stay out, and so does logging bootstrap.** | JWT signing keys and the seeded admin password in a collection means a database dump mints tokens. The logger is created in phase 1 and must write before Mongo is reachable. The rule in §2.1 is mechanical so nobody has to argue it per variable. |
| Each module defines its schema in `module.config` | **Yes.** `module.config.ts` becomes a declaration (`defineConfig({ schema })`) instead of a factory that reads `Environment`, and it is the file's only export. | The factory pattern exists because values came from env. With a schema, the same file gives validation on write, defaults on first boot, the generated types (`tulipes sync` already types the namespace via `typeof import`, it will read `schema` instead of `ReturnType`), the admin console's form, and the JSON Schema an agent needs. One declaration, five consumers. |
| "Inject as a plugin to mongoose" | **No, different mechanism.** A mongoose plugin mutates *other* schemas; what is wanted is a store that each module contributes a namespace to. | The settings store is a provider capability like `models`, with the Mongo implementation in `@tulipes/mongoose` and a file-backed one in core so the minimal preset (no database) keeps working. | A module folder holds only `module.config`, `module.acl`, `package.json` | **Yes.** `meta.variables.json` folds into `package.json` under `tulipes.env`; `index.ts` moves to `lib/` behind `package.json` `exports`; `schemas.ts` moves to `schemas/`. | `package.json` is already the manifest the boot reads without executing code, which is the property `meta.variables.json` existed for. Env shrinks to a handful of entries per app, so it no longer deserves a file. |
| API only, no frontend | **Already true in the runtime; make the generated app match.** | Nothing serves HTML. | An `ai-agent` folder per module | **Yes, but derive first and declare second.** `agent/<module>.agent.ts` lists tools; a tool is either a reference to a route's RAI (free: name, description, input schema and permission already exist) or an explicit action with a zod input and a handler. | Every endpoint already declares `id`, `name`, `description`, `folder` and zod `body`/`query`/`params`/`returns`. `@tulipes/spec` already turns those into JSON Schema. Rewriting that by hand per tool would drift the way `example/` and `init.ts` drift today. The folder is for what cannot be derived: module summary, curated exposure, and actions that are not endpoints. |

Two things the brief does not mention that decide whether 0.11 is actually
simpler:

- `packages/cli/src/init.ts` is 6,659 lines of embedded strings mirroring
  `example/`, kept honest by a CI diff. Every change in this plan touches both.
  §2.7 makes the example the template.
- `settings` is 17 files of hardened code (S08a to S08m). The database
  store takes over the job of all but the log stream, so the module shrinks
  to one endpoint and its two tailing helpers (§2.6).

## 2. Design

### 2.1 Two layers of configuration

**Environment** is what the process needs before the settings store can
answer, plus secrets. Declared in `package.json`, read with
`Environment.get()`, resolved once at boot exactly as today. The test is
mechanical:

> A value is an environment variable only if (a) boot needs it before a
> database connection exists, or (b) it is a secret. Everything else is a
> setting.

The production preset's environment after 0.11:

| Module | Variables |
|---|---|
| core | `PORT`, `MONGO_URI`, `REDIS_URL`, `LOG_LEVEL`, `LOG_DIR`, `LOG_CONSOLE`, `LOG_FILE` |
| auth | `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `AUTH_ADMIN_EMAIL`, `AUTH_ADMIN_PASSWORD` |

Eleven, down from 32. `LOG_BASENAME`, `LOG_ERROR_BASENAME`, the rotation and
retention variables become constants in the sys core module's logger (they
have never needed to differ per deployment). Everything in `security`,
`users`, `hello`, `PUBLIC_DOMAIN`, the JWT TTLs and `AUTH_RATE_LIMIT` become
settings.

**Settings** are declared per module with a zod schema, stored per module
namespace, validated on every write, hot-applied, and read through
`ctx.config.<module>` exactly where they are read today.

```ts
// modules/users/module.config.ts — the file's only export
import { defineConfig } from "@tulipes/core/config";
import { z } from "zod";

export default defineConfig({
  schema: z.object({
    maxSessions: z.number().int().positive().default(5)
      .describe("Max concurrent sessions per user"),
    signupMode: z.enum(["open", "invite", "closed"]).default("open")
      .describe("Who can register"),
  }),
  /** Optional. Called after a write lands, in every process that holds the app. */
  onChange(next, ctx) {},
});
```

Rules that keep this simple:

- Every field has a default. A namespace with no stored document is its
  defaults; first boot writes them. There is no "required setting" because
  an operator cannot be asked for a value the process needs to boot.
- No secrets in a schema. `defineConfig` rejects a field whose metadata says
  `secret`; the console never has to redact.
- Read at use time. `ctx.config.users.maxSessions` is live after a write;
  a value captured into a closure at boot is not. Modules that build
  something from a setting (the rate limiter, the CORS middleware, the body
  parser's limit) rebuild it in `onChange`.
- A field that cannot be hot-applied is tagged `.meta({ restart: true })`
  (zod 4). A write to it persists, applies on next boot, and the response
  says `requires_restart`. This replaces the whole restart_required /
  shadowed machinery with one flag.
- `config/app.config.ts` stays as the code-level seed for values that are
  app policy and belong to no module (`app.name`, `api.prefix`, locales,
  pagination). It is the one place that remains a plain function.

### 2.2 Lifecycle: bootstrap is the only hook

0.10's `module.config.ts` exports `onReady`, `onDrain` and `onShutdown`. In
the reference app `onReady` only logs, `onDrain` serves one SSE endpoint,
and `onShutdown` closes the cache. 0.11 removes all three. Initialization
is `bootstrap/*.bootstrap.ts`, which already exists, and a bootstrap
function may return its own cleanup:

```ts
// modules/core/bootstrap/cache.bootstrap.ts
import type { Ctx } from "@tulipes/core/boot";

export default async function cache(ctx: Ctx) {
  const client = openCache(ctx);
  return () => client.quit();   // optional; core runs it on shutdown, reverse load order
}
```

- **Every mode runs bootstrap**, including `script`, because it is now the
  only place a module opens a resource. A seed that should not run from a
  one-off script checks `ctx.mode === "script"` and returns. Seeds were
  already required to be idempotent.
- **Cleanups run after traffic drains**, in reverse load order, under the
  same deadline as today's `onShutdown`. Dependencies are still alive when a
  module's cleanup runs.
- **Long-lived work watches `ctx.signal`**, an `AbortSignal` core aborts
  the moment shutdown begins, before HTTP stops accepting. An SSE handler
  ends its response on it; a poller stops its loop. This is what `onDrain`
  did, as a standard Node idiom instead of an export.

A bootstrap file runs after settings are loaded and before routes mount, so
it can read `ctx.config` and `ctx.models` and cannot see `ctx.app`.

### 2.3 The settings store is a provider capability

Core defines the contract and ships the file-backed store; the persistent
store lives in `@tulipes/mongoose`.

```ts
// @tulipes/core/config
interface SettingsStore {
  load(namespace: string): Promise<StoredSettings | undefined>;   // { values, version, updated_at, updated_by }
  save(namespace: string, values: unknown, expectedVersion: number, actor: Actor): Promise<StoredSettings>;
  watch?(onChange: (namespace: string, stored: StoredSettings) => void): () => void;
}
```

| Store | Package | Selected when | Backing |
|---|---|---|---|
| file | `@tulipes/core` | no `tulipes.providers.settings` declared | `config/settings.<APP_ENV>.json`, one object keyed by namespace; watched with `fs.watch` |
| mongo | `@tulipes/mongoose` | `"providers": { "settings": "@tulipes/mongoose" }` | collection `settings`, one document per namespace |

The Mongo document:

```jsonc
{ "_id": "users", "values": { "maxSessions": 5, "signupMode": "open" },
  "version": 3, "updated_at": "…", "updated_by": { "id": "…", "email": "…" } }
```

Writes are `findOneAndUpdate` on `{ _id, version: expected }` so two
operators cannot overwrite each other. The previous document goes to
`settings_history` so a bad change can be reverted; history is read by the
console, never by boot.

Propagation across replicas: the store opens a change stream when the
connection is to a replica set (the failure smoke already runs one), and
polls `version` otherwise. Each process validates the incoming values
against the module's schema before swapping them in; an invalid document
written by hand is logged and ignored, never applied.

The minimal preset gets a real settings store for free, the file one, and
the console's write endpoint works against it the same way. Local
development on the production preset can also choose the file store.

### 2.4 Boot order

The config phase moves after the models provider, because the store needs
the connection. Bootstrap tasks move out of the models provider's `acquire`
so they run against a loaded config, in every mode.

```
 1  Environment      .env.<APP_ENV> + every package.json tulipes.env → validate
 2  Module graph     tulipes keys → tier / priority / topological sort
 3  Exploration      conventional paths resolved, nothing imported
 4  Declarations     module.config.ts imported: schemas + onChange, no values yet
 5  Models           provider connects and compiles models (no bootstrap)
 6  Settings         store loads every namespace → validate → seed defaults → ctx.config
 7  Translations
 8  ACL
 9  Bootstrap        bootstrap/*.bootstrap.ts in load order, every mode; cleanups collected
10  Queues, sockets  as today
11  fork             backend | worker | script
12  Banner           lists each namespace's store, version and last writer
    shutdown         ctx.signal aborts → http stops accepting + providers drain →
                     bootstrap cleanups in REVERSE order → providers disposed in reverse
```

The models provider contract becomes `contract: 2`: `acquire` returns the
capability without running bootstrap. `@tulipes/mongoose` already has
`runBootstrap` as an option, so the split is small; the bootstrap runner
itself moves into core because it no longer depends on a database.
Capability order is models → settings → queues → sockets; a settings
provider without a models provider is a declaration error reported in
phase 5b, as today.

Phase 4 is new and imports `module.config.ts` before the database exists.
This is the one place module code runs early, so the rule is: a
`module.config.ts` may import zod and types and nothing that touches
infrastructure. The reference core module's `registerBasePlugins()` at
module top level moves to a bootstrap file, where every other side effect
now lives.

### 2.5 The module layout

```
modules/billing/
  package.json          manifest: name, tulipes { tier, priority, dependsOn, requires, env }
  module.config.ts      settings schema + onChange
  module.acl.ts         grants

  routes/     *.routes.ts        controllers/  *.controllers.ts
  models/     *.model.ts         schemas/      *.schemas.ts
  bootstrap/  *.bootstrap.ts     helpers/
  queues/     *.queues.ts        sockets/      *.sockets.ts
  i18n/       <locale>.json      agent/        *.agent.ts
  lib/        index.ts           tests/        *.test.ts
```

- `tulipes.env` in `package.json` carries the entries `meta.variables.json`
  carried, same schema, same validation. `discoverModuleMeta` reads the
  manifest instead of a second file.
- `lib/index.ts` is the module's public surface and `package.json` points at
  it: `"exports": { ".": "./lib/index.ts" }`. `@app/core` keeps working
  unchanged for importers.
- The explorer reports any other `.ts`, `.js` or `.json` file at the module
  root as a boot error naming where it belongs. Markdown and dotfiles are
  ignored.
- `tulipes new module` scaffolds this layout and nothing else; the
  "delete what you do not need" step stays.

### 2.6 What becomes of `settings`

| Endpoint today | 0.11 |
|---|---|
| `GET /settings/modules` | `GET /config` in the `config` sys module: every module's manifest, environment (names, source, redacted), settings schema, values, version |
| `GET /settings/variables/:name` with `?reveal` | removed; there are no editable secrets, and env is read-only in the console |
| `PUT /settings/variables/:name` + `.env` editing | `PATCH /config/:module`: validated against the schema, optimistic version, audited, hot-applied; `requires_restart` only for tagged fields |
| `POST /settings/reboot` (PM2) | removed; nothing needs a restart to take effect |
| `GET`/`PUT /settings/i18n/:module/:locale` | removed; translations are code, edited in the repository |
| `GET /settings/logs/stream` (SSE) | **kept**, the module's only endpoint; ends its stream on `ctx.signal` |
| audit model | moves to `config` |

`settings` keeps `routes/`, `helpers/log-stream.ts`, `helpers/log-tail.ts`,
`schemas/` and its ACL grant; `env-file`, `files`, `pm2`, `access-lease`,
`audit`, the audit model and the controller's other methods go. The S08
items that covered the removed surface (S08a restart scope, S08d durable
audit before action, S08g constrained files, S08i restart acceptance) are
retired with it; S08h bounded history, S08l authorization throughout a
stream and S08m signalling at shutdown still apply and keep their tests.

`config` is a thin generated sys module: routes, ACL (`config:read` to
`admin` and `sysadmin`, `config:write` to `sysadmin` only), one audit model.
The validation, the store and the hot-apply live in core, so a fix reaches
every app through the library rather than as a generated-code migration,
which is the pain S14.4 recorded. The `sysadmin` boundary stays as the
security model describes it.

### 2.7 The agent surface

A tool is the unit an agent sees: a name, a description, a JSON Schema
input, and a permission. Most of a module's tools are its endpoints, which
already declare all four through `rai()`. The `agent/` folder adds what
cannot be derived.

```ts
// modules/hello/agent/hello.agent.ts
import { defineAgent } from "@tulipes/core/agent";
import { z } from "zod";

export default defineAgent({
  summary: "Greets callers and counts how often each greeting is used.",
  tools: [
    // Derived: name, description, input schema and permission come from the RAI.
    { route: "hello:greet-name" },
    { route: "hello:list-greetings", description: "List greetings, most used first" },

    // Declared: an action that is not an endpoint. The id is a RAI-style
    // permission, granted in module.acl.ts like any other.
    {
      id: "hello:reset-counts",
      description: "Reset the usage counter of every greeting",
      input: z.object({ confirm: z.literal(true) }),
      handler: async ({ models }, input) => {
        await models!.get("Greeting").updateMany({}, { times_used: 0 });
        return { reset: true };
      },
    },
  ],
});
```

What core does with it:

- **Manifest.** `ctx.agent.manifest(role?)` returns every module's summary
  and tools, each as `{ name, description, input_schema, permission,
  transport }` where `transport` is `{ method, path }` for a route or
  `{ action }` for a handler. Filtered by role so an agent only sees what
  its identity may call. `tulipes agent manifest` writes it as JSON offline,
  the same way `tulipes spec --offline` works.
- **Names.** Tool names must satisfy `^[a-zA-Z0-9_-]{1,64}$` for the Claude
  API and MCP alike, so `hello:greet-name` becomes `hello_greet_name`;
  collisions are a boot error. Input schemas are emitted with
  `additionalProperties: false` and `required`, which is what strict tool
  use needs. Route tools get `readOnly: true` when the method is `GET`.
- **Invocation.** Declared actions run through the same gate as routes: the
  ACL decides on the tool's id, `req.auth` or the MCP identity is the actor,
  input is validated with the zod schema, output goes through the envelope.
- **Transports.** Two, both thin: an HTTP pair in a generated sys module
  (`GET /agent/tools`, `POST /agent/tools/:name` for actions; route tools
  are called at their own path), and a stdio MCP server in a new
  `@tulipes/mcp` package that boots the app in script mode and serves the
  manifest as MCP tools. The MCP dependency never enters core.
- **Settings are tools too.** The `config` sys module's read and write
  endpoints are route tools, so an agent with `sysadmin` can reconfigure
  the app through the same door an operator uses, with the same audit.

Routes that should not be exposed to agents opt out with `agent: false`
on the RAI; a module without an `agent/` folder exposes every route by
default, so an app is agent-visible without doing anything.

### 2.8 The generator stops embedding strings

`tulipes init` copies a template tree instead of rendering 6,659 lines of
string literals. The tree is `example/`, packed into `packages/cli/templates/app/`
by `scripts/artifacts.mjs` at build. Presets and the two opt-outs are a
file-level manifest (which paths each preset includes) plus three token
substitutions (app name, core version, CLI version). The CI parity diff
becomes a check that the packed template equals the example, which is a
single `diff -r`.

This is the change that makes everything above cheap to maintain: a module
layout change is one edit in `example/`, not two.

### 2.9 Why the declaration is zod, not a mongoose schema

- Core cannot import mongoose: the minimal preset has no models provider,
  and `scripts/artifacts.mjs verify` fails the build if core gains the
  dependency. The declaration has to be in a library core already has.
- A mongoose schema validates through a document on a model on a
  connection. Settings validate on every write, on every replica when a
  change arrives, and in the file store where no connection exists. Zod
  validates a plain object anywhere and yields the field-level issues the
  envelope already renders for request bodies.
- `z.output<typeof schema>` is what `tulipes sync` needs to type
  `ctx.config.users.maxSessions` as `number`. Mongoose's `InferSchemaType`
  flattens enums to `string` and pulls mongoose types into code that never
  otherwise sees them.
- Zod 4 ships `z.toJSONSchema`, which gives the console its form metadata
  and the agent manifest its input schema in one call. Mongoose has no
  equivalent.
- Routes already validate `body`, `query` and `params` with zod. One
  vocabulary for everything input-shaped, for developers and for agents.

Mongoose still owns storage: the `settings` collection has a fixed mongoose
schema in the provider, with `values` as a mixed object, a version and the
audit fields. The zod schema describes what is allowed inside `values`. A
setting that needed an index or a reference to another collection would be
the signal to make it a model instead; nothing in the current app does.

### 2.10 Smaller changes that follow

- **zod 4.** Core moves to `zod@^4` so `defineConfig`, `rai()` and the
  agent manifest share one `z.toJSONSchema`, and `@tulipes/spec` drops its
  own converter. Generated apps already import `zod/v4`.
- **`tulipes sync`** generates `KnownVariables` from `tulipes.env` and the
  config namespace as `z.output<typeof import(...).default.schema>`. It still
  never executes module code.
- **`tulipes config:check`** boots in inspect mode and reports each
  namespace: source, version, invalid stored values, fields the schema no
  longer has.
- **Startup banner** gains a settings line per module: `users  settings
  mongo v3 (updated 2m ago by admin@example.com)`.
- **AGENTS.md rules** 1 and 5 are rewritten: "a per-deployment fact or a
  secret is an environment variable in package.json; everything else is a
  setting in module.config.ts" and "run `yarn sync` after touching
  package.json `tulipes.env` or a settings schema". Rule 4's "`app.ts`
  stays three lines" gains "and `module.config.ts` has one export". The
  `tulipes-settings` skill becomes `tulipes-config`; a `tulipes-agent-tool`
  skill is added.

## 3. Rejected alternatives

- **A mongoose plugin per module** that attaches settings to schemas: wrong
  tool. Plugins extend documents; settings are one document per module.
- **All configuration in the database**, secrets included: a dump mints
  tokens, and boot cannot read the store before it has the connection
  string. The rule in §2.1 is the honest version of "everything".
- **Keeping `onShutdown` as a second hook** next to bootstrap: two places
  to open and close the same resource. A cleanup returned from the function
  that opened it cannot drift from it.
- **An `actions/` layer** that both routes and tools bind to: one more
  concept for every endpoint, to serve the minority of tools that are not
  endpoints. Deriving tools from routes and declaring the rest gets the
  same result without touching how routes are written.
- **Settings in core only, no provider seam:** would put a Mongo driver in
  core, which `scripts/artifacts.mjs verify` exists to prevent.
- **Extracting auth into a library in the same release:** S14.4's reasons
  still hold; one breaking line at a time.

## 4. What stays exactly as it is

RAI and the ACL, the response envelope, `defineRoutes()` and offline
inspection (unless card 9.1 is pulled in), the module graph, translations,
the three process modes, the shutdown deadline and reverse ordering, the
models, queues and sockets providers' contracts (beyond the bootstrap
split), the production preset's auth module, and the Vitest suites. 0.11 is
a change in where values live and what a module folder looks like, not in
how a request is handled.

## 5. Sprint breakdown

Ordered so that each sprint leaves `master` green and every earlier sprint's
tests still pass. No dates; sizes are relative. Commit messages carry the
item id, as AGENTS.md asks.

### 0.11-S01 — Settings contract and lifecycle in core (medium)

- S01.1 `defineConfig({ schema, onChange })` in `@tulipes/core/config`;
  rejects secrets, non-object schemas, fields without defaults and any
  other export from `module.config.ts`.
- S01.2 Boot phase 4 (declarations), phase 6 (settings) and phase 9
  (bootstrap in core, every mode, cleanups collected), each with its own
  aggregate report; provider contract 2 with the bootstrap split;
  capability order models → settings → queues → sockets.
- S01.3 `ctx.signal`; cleanups run after drain in reverse order under the
  existing deadline; the three lifecycle exports are a boot error that
  names the replacement.
- S01.4 File store, `fs.watch`, `onChange`, `restart` metadata and
  `requires_restart`.
- S01.5 `tulipes sync` types from the schema; `tulipes config:check`.
- S01.6 zod 4 in core and spec.

**Acceptance:** a core-only fixture app declares two namespaces, boots with
defaults, writes a value through the store, sees `ctx.config` change and
`onChange` fire without restart; an invalid stored file is reported, not
applied; a bootstrap cleanup runs after the server closes and its
dependency's cleanup runs after it; a handler holding `ctx.signal` ends
within the deadline; `test:types` proves `ctx.config.users.maxSessions` is
`number`.

### 0.11-S02 — Mongo settings store (medium)

- S02.1 `@tulipes/mongoose` exports the `settings` provider; document shape,
  optimistic version, `settings_history`.
- S02.2 Change stream on replica sets, polling otherwise; validation before
  apply.
- S02.3 Integration tests against `TEST_MONGO_URI`; a propagation case in
  `failure-smoke.mjs` against the three-node set.

**Acceptance:** two booted processes on one database; a write in one is
visible in the other within the poll interval, and immediately on the
replica set; concurrent writes with a stale version are refused with the
current document.

### 0.11-S03 — Manifest env and module layout (small)

- S03.1 `tulipes.env` in `package.json`; `meta.variables.json` is a boot
  error that names the move.
- S03.2 Explorer rule for the module root; `lib/` with `exports`;
  `schemas/`.
- S03.3 `tulipes new module` scaffolds the layout, including `agent/` and
  a bootstrap file that returns a cleanup.

**Acceptance:** core tests cover the root rule and the manifest env; the
scaffolded module boots, typechecks and appears in the banner.

### 0.11-S04 — Agent surface (medium)

- S04.1 `defineAgent`, derived and declared tools, naming, manifest with
  role filtering, `agent: false` on RAI.
- S04.2 `tulipes agent manifest` (offline).
- S04.3 Action invocation through the ACL gate and the envelope.
- S04.4 `@tulipes/mcp`: stdio server over the manifest, identity by API
  token or `--as`.

**Acceptance:** the manifest of the reference app is generated offline and
round-trips through a strict-mode tool definition validator; a declared
action denied by the ACL returns 403 through HTTP and an MCP error through
stdio; a `GET` route tool is marked read-only.

### 0.11-S05 — Reference app on 0.11 (large)

- S05.1 Every module relaid per §2.5; env shrunk per §2.1; each module's
  schema written with descriptions; `onReady`/`onShutdown` bodies moved to
  bootstrap files; `registerBasePlugins()` to a bootstrap file.
- S05.2 `config` sys module (routes, ACL, audit) and `agent` sys module;
  `settings` reduced to the log stream per §2.6, ending on `ctx.signal`.
- S05.3 Security: rate limiter, CORS, body limit and HSTS rebuilt from
  `onChange`.
- S05.4 Skills and AGENTS.md updated; `tulipes-config` and
  `tulipes-agent-tool` written; `tulipes-settings` reduced to the stream.

## 9. Candidate cards: performance and developer experience

Not scheduled. Each is sized and independent; the recommendation is at the
end. They are listed because the line is already breaking, and a breaking
line is the cheapest moment for them.

### 9.1 Routes without `defineRoutes` and `runtime()` (DX, large)

Every routes file in the reference app wraps its controller in a lazy
import so that `tulipes spec --offline` and `tulipes routes --offline` can
load the file without infrastructure:

```ts
const hello = runtime(async ctx => {
  const { HelloController } = await import("../controllers/hello.controllers.js");
  return new HelloController(ctx);
});
router.get("/hello", rai({ id: "hello:greet" }), hello(value => value.greet()));
```

That is four concepts (`defineRoutes`, `runtime`, the wrapper call, the
`offline` manifest flag) and one rule ("offline modules must install custom
access checkers inside defineRoutes") in service of one CLI feature. The
framework already forbids infrastructure at import time: models are
declarations, the cache is lazy, bootstrap owns side effects in 0.11. So
inspection can import everything and acquire nothing: `boot({ inspect })`
hands providers a stub capability that throws on use, and a routes file is
a plain `(ctx) => Router` with statically imported controllers or inline
handlers. `defineRoutes`, `runtime()` and `offline` go. The one thing lost
is that a routes file whose import touches infrastructure fails inspection
instead of being tolerated, which is the right outcome.

### 9.2 One authenticated request costs three database reads (performance, medium)

`passport.ts` resolves a bearer token with `isRevoked` (a `RevokedToken`
read), `loadSession` (a `Session` read) and `findById` on `User`, then
`touchSession` writes at most once a minute. Plus the Redis call of the rate
limiter, that is four round trips before a handler runs. S08b and S08k made
revocation strict on purpose; the fix keeps that: cache the resolved
`{ session, user, credentialVersion }` in the app cache (Redis in
production, shared by replicas) keyed by session id with a TTL no longer
than `accessTtl`, and delete the key on every path that revokes: logout,
refresh reuse, password change, role change, session cap eviction. Reads
drop to one Redis call per request on a hit; the semantics are unchanged
because the same code that writes a revocation deletes the entry. This
sits entirely in the generated auth module.

### 9.3 Production without tsx (performance and operations, medium)

`start` is `tsx app.ts` and the PM2 ecosystem names tsx as interpreter, so
production transpiles on every cold start, carries esbuild in the install
and runs through a loader. Node 24 strips types natively, which removes
tsx from the runtime path entirely. The cost is a code-base rule: relative
imports must name `.ts` files (TypeScript 5.7's
`rewriteRelativeImportExtensions` keeps `tsc` output valid), and `enum`,
parameter properties and namespaces are out. The explorer already resolves
either extension. Alternative with no import change: a `tulipes build` to
`dist/` and `node dist/app.js`. Either way `tsx` stays for `yarn dev`.

### 9.4 Generated types for models and queues (DX, small)

`ctx.models.get<UserDoc>("User")` and `queues.add("hello.count-greeting",
data)` are strings with a caller-side generic; a typo is a runtime error and
`data` is `unknown`. `tulipes sync` already does `typeof import` on
`module.config.ts`; the same trick on `models/*.model.ts` and
`queues/*.queues.ts` gives `KnownModels` and `KnownQueues` augmentations,
so `ctx.models.get("User")` is typed from the model file's own schema and a
wrong name does not compile. No runtime change.

### 9.5 A testing package (DX, medium)

`example/tests/app.test.ts` is one file because every test has to boot the
app itself. A `@tulipes/testing` with `bootTestApp()` (file settings store,
random port, `handleSignals: false`, teardown), `request()` over `fetch`
with the envelope decoded, and a `login(role)` helper from the auth module
turns a module test into ten lines. The packed smokes keep covering the
real processes.

### 9.6 Two small gotchas removed (DX, small)

- `dependsOn` is derived from `dependencies` entries in the app's own scope
  (`@app/*`); explicit `dependsOn` remains for ordering without an import.
  The skills currently warn that forgetting either half fails differently.
- `routes.mount(app, apiPrefix, router)` with `apiPrefix` imported from
  `../../../config/routes.js` in every routes file becomes
  `routes.mount(router)` with the prefix from `config.api.prefix`, and a
  second argument only to override it.

### Recommendation

Pull 9.1, 9.4 and 9.6 into 0.11: they are all layout-level, land naturally
in S03 and S05 while every routes file is being relaid anyway, and they are
the changes a developer notices on day one. 9.2 is a contained change to
the generated auth module and can ship in a 0.11 patch with its own
regression against the S08b and S08k tests. 9.3 and 9.5 are independent of
the layout and belong to 0.12, where they can be measured on their own.
