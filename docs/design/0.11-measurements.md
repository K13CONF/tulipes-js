# 0.11 measurements

Two numbers the 0.11 plan (§7) asked for, with the conditions that produced
them. Both are reproducible with the commands shown; neither is a benchmark
of the framework, only a before/after of one change each.

## Cold start without tsx (S06.2)

**What:** time from `spawn` to the first `200` on `/health` of the minimal
preset, generated and installed from the packed 0.11 archives by
`scripts/scaffold-smoke.mjs .artifacts minimal` with `TULIPES_SMOKE_KEEP=1`.
The same installed app ran twice: as generated (`node app.ts`), and with
`tsx@4.23.15` added to it and the loader registered (`node --import tsx
app.ts`), which is how a 0.10 app starts. Five runs each, median reported,
`APP_ENV=development`, `PORT=0`, console and file logging off.

**Where:** the development container of 2026-10-07 — Linux 6.18, Node
22.22.0 (type stripping on by default), pnpm 10.28.0, no services (the
minimal preset declares none).

| start | median | min | max |
|---|---|---|---|
| `node app.ts` (0.11) | 343 ms | 337 ms | 422 ms |
| `node --import tsx app.ts` (as 0.10) | 577 ms | 547 ms | 724 ms |

The difference is the loader: nothing else in the two runs differs. The
script that took the numbers is below; it waits for the banner's URL, polls
`/health`, and stops the process with SIGTERM between runs.

```js
// coldstart.mjs <app dir> <node args…>
const child = spawn(process.execPath, args, { cwd, env: { ...process.env, APP_ENV: "development", PORT: "0", LOG_CONSOLE: "false", LOG_FILE: "false" } });
// read stdout until /http:\/\/[^\s]*:(\d+)/, then fetch /health until 200; record performance.now() − start
```

**Production preset, Node 24 (2026-10-08).** The reference app (`example/`,
eight modules, mongoose models and settings store, bullmq, socket.io) on
macOS (Darwin 25.2), Node 24.14.0, MongoDB 7.0 and Redis on localhost,
`APP_ENV=development`, `PORT=0`, console and file logging off, five runs
with SIGTERM between them. Measured from `spawn` to the banner's URL, since
the health route sits under the API prefix and the poll above was written
for the minimal preset; the banner's own `ready in` (boot start to listen)
is shown beside it.

| `node app.ts` (0.11.0) | median | min | max |
|---|---|---|---|
| wall time to the banner | 532 ms | 500 ms | 886 ms (first run, cold file cache) |
| the banner's `ready in` | 339 ms | 327 ms | 626 ms (first run) |

The 0.10 comparison with `--import tsx` was not repeated here: the loader
difference is the one the minimal preset measured, and nothing in it depends
on the preset. The per-file test boot time remains unmeasured.

## Database reads on an authenticated request (S05.4)

**Before (0.10 and 0.11 before the cache):** resolving a bearer token read
MongoDB three times — `RevokedToken.countDocuments`, `Session.findOne` with
`Credential.findOne` for the version, `User.findById` — and wrote
`last_seen_at` when the session had not been touched for
`sessionTouchSeconds`. This is read from the auth module's passport strategy
and `loadSession()`, not timed.

**After:** a hit on the app cache (Redis in production, shared by every
replica) is one Redis read and no MongoDB read; the touch write still
happens when due. The reference app's `modules/auth/tests/auth.test.ts`
spies on `User.findById`, `User.findOne`, `Session.findOne`, `Session.find`
and `RevokedToken.countDocuments` across a warm `GET /auth/me` and asserts
none ran; a second test boots a second replica and asserts a logout, a
password change, a session end and a soft delete on one are refused on the
very next request on the other. Both need MongoDB and run in CI; their
status is what this section reports, not a local timing.
