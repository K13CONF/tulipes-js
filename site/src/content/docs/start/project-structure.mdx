An app generated with `tulipes init --preset production` is a complete
application you own. This page walks through it top to bottom so you know
where each kind of code lives before you write any. The minimal preset is a
subset of the same layout.

## The entrypoints

There is one codebase and three processes. Each entrypoint is a few lines,
and the only difference between the first two is the mode:

```ts title="app.ts"
import { boot } from "@tulipes/core/boot";

await boot({ rootDir: import.meta.dirname, mode: "backend" });
```

```ts title="worker.ts"
import { boot } from "@tulipes/core/boot";

// Worker mode refuses to start until at least one module registers a
// queue processor — a consumer with nothing to consume is a
// misconfigured deployment, not a valid idle state.
await boot({ rootDir: import.meta.dirname, mode: "worker" });
```

- `app.ts` (`pnpm dev`, `pnpm start`) serves HTTP and Socket.IO.
- `worker.ts` (`pnpm worker`) consumes the queues every module declares.
- `mcp.ts` (`pnpm mcp`) boots in script mode and serves the modules' agent
  actions to an MCP client such as Claude Code, through `serveMcp()` from
  `@tulipes/mcp`. It is experimental; see the [MCP guide](/tulipes-js/guides/mcp/).

Keep entrypoints this small. Global middleware belongs to a sys-tier module,
never to `app.ts`. [Process modes](/tulipes-js/concepts/process-modes/)
explains what each mode runs.

## package.json

The root manifest selects the providers, which is the whole of the
infrastructure choice:

```json title="package.json"
{
  "tulipes": {
    "providers": {
      "models": "@tulipes/mongoose",
      "settings": "@tulipes/mongoose/settings",
      "queues": "@tulipes/bullmq",
      "sockets": "@tulipes/socket.io"
    }
  }
}
```

Its scripts are the daily commands: `dev`, `start`, `worker`, `mcp`, `sync`,
`check` (`tulipes env:check`), `typecheck`, `test`, `spec`, `manifest`,
`script` (plain `node`, for `pnpm script scripts/x.ts`) and the `pm2:*`
family. `pnpm-workspace.yaml` lists `modules/*`, which makes every module a
package the app depends on by name.

## config/

`config/app.config.ts` is the app-wide seed: values no single module owns,
and the wiring from environment values to the keys core and the providers
read. It receives every module's environment values as `env`, typed:

```ts title="config/app.config.ts"
const appConfig = ((env) => ({
  app: { name: "bookstore" },
  api: { prefix: "/api/v1" },
  server: { port: env.core.port },
  mongoose: env.core.mongodbUri
    ? { uri: env.core.mongodbUri }
    : { uri: env.core.mongodbHost, user: env.core.mongodbUsername, pass: env.core.mongodbPassword, dbName: env.core.mongodbDbName },
  bullmq: { redisUrl: env.core.redisUrl },
  i18n: { defaultLocale: "en", supportedLocales: ["en", "fr"] },
  timezone: { default: "UTC" },
  pagination: { defaultLimit: 20, maxLimit: 100, maxTimeMs: 5_000 },
})) satisfies AppConfigFn;
```

The generated file carries a comment on every key. `api.prefix` is where
every router a routes file returns is mounted, so `/api/v1` is a one-line
change here. `config/mcp.config.ts` tells `pnpm mcp` how to identify the
caller from its token. [Configuration layers](/tulipes-js/concepts/configuration/)
explains how this seed, module settings and environment values combine.

## modules/

Every feature is a folder under `modules/`, and every module is a workspace
package with its own `package.json`. A module's root holds exactly
`package.json`, `module.config.ts` and `module.acl.ts`; everything else has
a folder, and the boot refuses a stray root file. Here is `hello`, the
module that exercises every contract:

<FileTree>
- modules/hello/
  - package.json name, tier, priority, dependencies, environment values
  - module.config.ts settings schema, read at ctx.config.hello
  - module.acl.ts permission grants
  - routes/
    - web/
      - hello.routes.ts
      - hello.greetings.routes.ts
  - controllers/
    - web/
      - hello.controllers.ts
      - hello.greetings.controllers.ts
  - helpers/ plain functions, no framework
  - models/
    - greeting.model.ts
  - bootstrap/
    - seed-greetings.bootstrap.ts
  - queues/
    - hello.queues.ts
  - sockets/
    - hello.sockets.ts
  - agent/
    - hello.agent.ts
  - i18n/
    - en.json
    - fr.json
  - tests/
    - hello.test.ts
</FileTree>

| Folder or file | What it holds | Read by |
|---|---|---|
| `package.json` | the `tulipes` key: `tier`, `priority`, `dependsOn`, `env` | the boot, before any code runs |
| `module.config.ts` | `defineConfig({ schema })`: settings an operator may change at runtime | every process |
| `module.acl.ts` | `acl.allow(role, ...ids)` on this module's ids | every process |
| `routes/*.routes.ts` | `(ctx) => Router`, one `rai()` per endpoint | backend, and inspection |
| `controllers/` | classes holding `ctx`, one method per handler | imported by routes |
| `schemas/*.schemas.ts` | zod request and response shapes | imported by routes |
| `helpers/` | logic shared by a route and an agent action | imported directly |
| `lib/index.ts` | what other modules may import, as `@app/<name>` | other modules |
| `models/*.model.ts` | `{ name, schema }`, a declaration | the models provider |
| `bootstrap/*.bootstrap.ts` | idempotent initialization, may return a cleanup | backend and worker |
| `queues/*.queues.ts` | `jobs` schemas and `(ctx, queues) => …` | every process; consumed in the worker |
| `sockets/*.sockets.ts` | `(ctx, sockets) => …` claiming a namespace | backend only |
| `agent/*.agent.ts` | `defineAgent({ summary, actions })` (experimental) | every process |
| `i18n/<locale>.json` | this module's strings; the module is the namespace | every process |
| `tests/` | vitest files booting the app with `@tulipes/testing` | `pnpm test` |

The [modules concept page](/tulipes-js/concepts/modules/) covers the
manifest keys and load order in depth.

### The modules the preset ships

Load order is tier first (`sys` before `app`), then `priority`, then
`dependsOn`. The three sys modules form the head of every request:

- **`core`** (sys, 0) declares the infrastructure variables (`PORT`,
  `MONGO_URI`, `REDIS_URL`, `LOG_*`), registers the Mongoose base plugins,
  and exports shared helpers as `@app/core`: `moduleLogger`, the cache, the
  list-query language (`listQuery`, `toMongoose`, `runQuery`), `lazy()` and
  `baseSchemaOptions`. Its routes file is the global middleware slot.
- **`security`** (sys, 10) mounts helmet, CORS, request logging, body
  parsing with a size limit, proxy trust and Redis-backed rate limits.
  Everything it does is a setting in its `module.config.ts`.
- **`auth`** (sys, 20) resolves `req.auth` for every request from a bearer
  token, defines the roles, seeds the admin account on first boot, and
  serves `/auth/login`, `/auth/register`, `/auth/refresh`, sessions and API
  tokens. Its `module.acl.ts` is where a new feature module's namespace is
  granted to `admin` and `sysadmin`.
- **`users`** owns the `User` model and a back office under `/users`.
- **`settings`** and **`config`** are the operator console: describing
  every module and changing settings at runtime.
- **`hello`** is the example to copy from.
- **`agent`** and **`agents`** expose agent actions over HTTP and run
  Claude against them as queue jobs (both experimental).

## types/ and .env.example

Both are generated by `pnpm sync` from the modules, and `pnpm dev` runs it
on every start. `types/tulipes.d.ts` types `ctx.config`, the environment
values, the model names and the queue payloads; never edit it. `.env.example`
lists every variable any module declares, grouped, and is the committed
contract you copy into `.envs/`.

## .envs/

One file per `APP_ENV`: `.env.development`, `.env.staging`,
`.env.production`. They are git-ignored, because they hold working
credentials. Resolution order is `process.env`, then
`.envs/.env.<APP_ENV>`, then each variable's declared default, so a value
injected by the container always wins. The staging and production files are
generated with the secrets left blank on purpose. See
[environment variables](/tulipes-js/guides/environment-variables/).

## scripts/

One-off tasks that boot the real app in `script` mode: every phase the
backend runs, then nothing is started. Run them with `pnpm script`:

```sh
pnpm script scripts/count-greetings.ts
```

Every script follows the same shape, with `shutdown()` in a `finally`, or
the open MongoDB and Redis handles keep the process alive:

```ts title="scripts/count-greetings.ts"
const handle = await boot({ rootDir: join(import.meta.dirname, ".."), mode: "script" });

try {
  const { models, config } = handle.ctx;
  const greetings = await models!.get("Greeting").find().select("name times_used -_id").lean();
  console.log(`${config.app?.name} — ${greetings.length} greeting(s)\n`);
  console.table(greetings);
} finally {
  await handle.shutdown();
}
```

`scripts/deploy-nginx.ts` renders the nginx template for the current
`APP_ENV`, installs it and reloads nginx. See [scripts](/tulipes-js/guides/scripts/).

## nginx/ and ecosystem.config.cjs

`nginx/<APP_ENV>.conf` are templates with `{{DOMAIN}}` and `{{PORT}}`
placeholders, filled in by the deploy script, with Socket.IO upgrade headers
and a commented TLS block. `ecosystem.config.cjs` defines the two PM2 apps,
the backend and the worker, for development, staging and production, with a
`kill_timeout` of 10 seconds so a graceful shutdown can drain queues. Both
are covered in the [production section](/tulipes-js/production/deployment/).

## tests/ and vitest.config.ts

`tests/app.test.ts` checks the app as a whole; each module's own tests live
in `modules/<name>/tests/`. `tests/support.ts` builds the environment every
test boot uses from `TEST_MONGO_URI` and `TEST_REDIS_URL`, so the suite never
touches your development data. `vitest.config.ts` runs files one after
another (`fileParallelism: false`), because every file boots the app against
the same services.

## AGENTS.md, CLAUDE.md and .claude/

`AGENTS.md` is the vendor-neutral file coding agents read: the
non-negotiable rules (never read `process.env`, every route declares a RAI,
every response goes through `res.respond`, models are declarations), where
each kind of code goes, and the commands. `CLAUDE.md` points Claude Code at
it. `.claude/skills/` holds one guide per convention (module, endpoint,
environment variable, model, queue, socket, permissions, list query, i18n,
spec, boot errors and more), loaded on demand. They are plain markdown, so
they are worth reading yourself.

## logs/ and docs/

`logs/` is written at runtime by the core module's logger: JSON-line files
per process mode (`app-backend.<date>.log`, `app-worker.<date>.log`) and an
errors-only copy, because backend and worker run at the same time and must
not rotate one file. `docs/` receives the generated OpenAPI document, Postman
collection and agent manifest; `docs/browser-auth.md` explains the token
transport for browser clients.

<Aside type="tip">
When you wonder where something goes, `AGENTS.md` has a "Where things go"
table. A connection string goes in a module's `tulipes.env`, a value an
operator may change goes in its `module.config.ts`, and a helper two modules
share goes in `modules/core` behind `@app/core`.
</Aside>
