Tulipes is a TypeScript framework for building HTTP APIs on Express 5. You
write **modules**, one folder per feature, and Tulipes discovers them, orders
them, checks everything it can about them, and wires them into a running app.
When something is wrong it refuses to start, and it tells you every problem at
once rather than one per restart.

## The problem it solves

A plain Express app starts simple and drifts. Routes live in one folder,
models in another, permissions in a middleware file, environment variables are
read with `process.env.X` wherever someone needed one, and every new feature
touches six places. Mistakes surface late: a missing variable is `undefined`
at the first request that reads it, a route someone forgot to protect is
public, an error handler leaks a stack trace.

Tulipes moves those failures to boot time. This is what the production
starter prints when it is started with `APP_ENV=production` and none of its
secrets set. It exits before listening, and it names all five problems:

```txt
TulipesBootError: Boot aborted during "environment" — 5 issue(s):
  ✖ [auth] required variable "JWT_ACCESS_SECRET" has no value (Signing key for short-lived access tokens)
  ✖ [auth] required variable "JWT_REFRESH_SECRET" has no value (Signing key for refresh tokens; separate from the access key so leaking one cannot mint the other)
  ✖ [auth] required variable "AUTH_ADMIN_EMAIL" has no value (Email of the admin account seeded on first boot)
  ✖ [auth] required variable "AUTH_ADMIN_PASSWORD" has no value (Password for the seeded admin account; change it after the first login)
  ✖ [core] required variable "REDIS_URL" has no value (Redis connection string (queues, cache, rate limits))
```

## The ideas it is built on

<CardGrid>
  <Card title="Modules, not layers">
    A feature lives in one folder under `modules/`: routes, controllers,
    models, settings, permissions, translations, jobs and tests. Delete the
    folder and the feature is gone, with no registration left behind.
  </Card>
  <Card title="Fail closed">
    Missing variables, dependency cycles, duplicate grants and colliding queue
    names all stop the boot with a full report. A route without a permission
    id does not start. Unknown roles are denied, unrouted requests get a 404,
    and unexpected errors never leak internals outside development.
  </Card>
  <Card title="One codebase, three processes">
    The same app boots as a `backend` HTTP server, a `worker` that consumes
    queues, or a one-shot `script`. All three share the same modules and the
    same configuration, so a maintenance script sees exactly what the server
    sees.
  </Card>
  <Card title="Generated types">
    `tulipes sync` reads your modules and writes `types/tulipes.d.ts`: config
    namespaces, environment values, model names and queue payloads become
    types, so a misspelled config key or a wrong job payload does not compile.
  </Card>
  <Card title="Core owns no infrastructure">
    `@tulipes/core` installs no database, queue or socket driver. An app
    declares the providers it wants (`@tulipes/mongoose`, `@tulipes/bullmq`,
    `@tulipes/socket.io`) and installs only those.
  </Card>
</CardGrid>

## Compared with plain Express

Tulipes does not hide Express. Routes are ordinary Express `Router`s,
`req` and `res` are Express objects, and `res.json` still works. What
Tulipes adds sits around them:

| Concern | Plain Express | Tulipes |
|---|---|---|
| Where code goes | your convention | one folder per feature, fixed file roles |
| Environment | `process.env.X`, read anywhere | declared per module in `package.json`, validated at boot, read as `ctx.config.<module>.<name>` |
| Permissions | middleware you remember to add | every route declares a RAI id; a route without one refuses the boot; the ACL denies by default |
| Request validation | hand-written or a library | zod schemas on the route declaration, the same ones that generate OpenAPI |
| Responses | any shape | one envelope, `{ success, data, errors, meta }`, built by `res.respond()` and the error handler |
| Background jobs and sockets | separate wiring | `queues/*.queues.ts` and `sockets/*.sockets.ts` in the module, run by providers |
| API documents | maintained by hand | generated from the routes by `tulipes spec` |

Core mounts **no** middleware of its own. Your system-tier modules own the
head of the request pipeline (helmet, CORS, body parsing, authentication);
core guarantees only the tail: a 404 for anything unrouted and a terminal
error handler.

## Who it is for

Tulipes suits a team building a JSON API that will grow to many features and
several people, and that wants the framework to catch configuration and
permission mistakes before deployment. It is opinionated: Express 5, zod 4
and i18next are fixed choices, and the production starter assumes MongoDB and
Redis. If you want a database other than MongoDB today, you would write your
own models provider against the seam described in
[the provider contract](/tulipes-js/concepts/providers/).

It also suits AI-assisted work. Every generated app carries an `AGENTS.md`
and task-scoped skills under `.claude/skills/` that tell a coding agent the
conventions it would otherwise guess wrong. See
[AI-assisted development](/tulipes-js/guides/ai-assisted-development/).

## Stability

The current line is **0.13** (core 0.13.2). Its contracts are settled and a
breaking change waits for 0.14; patch releases preserve documented behavior.
Two caveats, stated plainly in the project's support policy:

- No production pilot has run the framework yet: there is no load,
  backup-restore or multi-replica evidence and no independent security review.
- The agent surface (`@tulipes/core/agent`, `agent/*.agent.ts` files, the
  `agent` and `agents` modules, `tulipes agent manifest`) and `@tulipes/mcp`
  are experimental and may change in any release.

Node 24.x is the only supported runtime. The
[changelog](/tulipes-js/production/changelog/) and
[upgrading guide](/tulipes-js/production/upgrading/) cover what changed
between lines.

<Aside type="note">
"Stable" here is a statement about the API, not about production hours.
Choose it accordingly, and read the [security model](/tulipes-js/production/security-model/)
before you deploy.
</Aside>
