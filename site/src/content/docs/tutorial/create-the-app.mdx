We start from the production preset, which gives us authentication, users,
settings, logging, queues and sockets already wired, so the rest of the
tutorial can be about books. In this chapter we scaffold the app, start its
two services, boot it, and see what Tulipes does when something it needs is
missing.

## Scaffold

```sh
tulipes init bookstore --preset production
cd bookstore
pnpm install
```

`init` writes the files and prints what to do next:

```txt
Project "bookstore" is ready. Next:

  cd bookstore
  npm install -g pnpm   # once per machine
  pnpm install
  pnpm dev

  → http://localhost:3000/api/v1/hello

Needs mongo and redis running — see MONGO_URI / REDIS_URL in
.envs/.env.development. Run `pnpm worker` in a second terminal to
consume queued jobs.
```

The [project structure](/tulipes-js/start/project-structure/) page tours
every file it created. For now, three matter: `package.json` declares the
providers, `config/app.config.ts` wires the environment to them, and
`.envs/` holds the environment.

## Start the services

The root `package.json` selects four providers:

```json title="package.json"
{
  "tulipes": {
    "providers": {
      "models": "@tulipes/mongoose",
      "settings": "@tulipes/mongoose/settings",
      "queues": "@tulipes/bullmq",
      "sockets": "@tulipes/socket.io"
    }
  }
}
```

Models and settings need MongoDB; queues need Redis (and so do the preset's
cache and rate limiter). Start both in Docker:

```sh
docker run -d --name bookstore-mongo -p 27017:27017 mongo:8
docker run -d --name bookstore-redis -p 6379:6379 redis:7
```

## The environment

`init` generated one file per environment under `.envs/`. Development is
filled in with working local values:

```sh title=".envs/.env.development"
PORT=3000
LOG_LEVEL=debug

MONGO_URI=mongodb://127.0.0.1:27017/bookstore
REDIS_URL=redis://127.0.0.1:6379

# Auth. Separate keys, so leaking one cannot mint the other.
JWT_ACCESS_SECRET=dev-only-access-secret-change-me
JWT_REFRESH_SECRET=dev-only-refresh-secret-change-me
AUTH_ADMIN_EMAIL=admin@example.com
AUTH_ADMIN_PASSWORD=dev-admin-password
```

Each variable is **declared** by a module, in the `tulipes.env` key of its
`package.json`. `REDIS_URL` belongs to the core module:

```json title="modules/core/package.json"
"redisUrl": {
  "key": "REDIS_URL",
  "type": "url",
  "group": "redis",
  "required": true,
  "description": "Redis connection string (queues, cache, rate limits)"
}
```

Nothing reads `process.env` directly. The value lands at
`ctx.config.core.redisUrl`, typed as a string, and `config/app.config.ts`
hands it to BullMQ as `bullmq: { redisUrl: env.core.redisUrl }`.

Check what every variable resolves to without booting:

```sh
pnpm check
```


Each line is a config path, the variable it came from and the value.
Secrets are masked. `MONGO_HOST` and its siblings show their defaults; they
are only used when `MONGO_URI` is empty. A value in the real environment beats the file, which
beats the declared default, so a container can always override what is
written here.

<Aside type="caution">
`.envs/` is git-ignored because these files hold credentials. The committed
contract is `.env.example`, regenerated by `pnpm sync` from every module's
declarations. On a fresh clone you copy it: `mkdir -p .envs && cp .env.example .envs/.env.development`.
</Aside>

## Boot

```sh
pnpm dev
```

```txt
  ▲ bookstore  development · backend mode

  ➜  Server      http://localhost:3000  ● listening
  ➜  Models      mongodb://127.0.0.1:27017/bookstore  ● ready  ·  mongoose
  ➜  Settings    mongodb://127.0.0.1:27017/bookstore.settings (poll)  ● ready  ·  mongoose-settings  ·  core v1, security v1, auth v1, users v1, hello v1, agents v1
  ➜  Queues      redis (3 queue(s))  ● ready  ·  3 processor(s) registered  ·  bullmq
  ➜  Sockets     /users, /hello  ● ready  ·  socket.io
  ➜  Modules     9 (core*, security*, auth*, users, hello, settings, config, agent, agents)  ·  * sys tier
  ➜  Locales     en, fr  ·  7 translated module(s)
  ➜  Time zone   UTC  ·  requests may ask for any zone  ·  process
  ➜  Roles       4 (guest, user, admin, sysadmin)
  ➜  Runtime     Node v24.22.2  ·  PID 4917  ·  ready in 1373ms
```

The banner is the checklist of what booted. Read it after every change:

- **Models** and **Settings**: the MongoDB connection is up. Settings are
  stored in the `settings` collection, one document per module, at version 1
  on a first boot. `(poll)` means other processes notice a change by polling,
  because a standalone MongoDB has no change streams; a replica set would use them.
- **Queues**: three queues are defined by the `hello`, `users` and `agents`
  modules, each with a processor. The backend only produces into them.
- **Sockets**: two namespaces are claimed.
- **Modules**: nine, in load order. The starred ones are the sys tier, which
  loads first and owns global middleware.
- **Roles**: defined by the auth module. On this first boot, the auth module
  also seeded an admin account from `AUTH_ADMIN_EMAIL` and `AUTH_ADMIN_PASSWORD`.

Call the example module:

```sh
curl http://localhost:3000/api/v1/hello
```

```json
{"success":true,"data":{"message":"Hello, world!","app":"bookstore"},"errors":[],"meta":{}}
```

The terminal running `pnpm dev` logs each request through the security
module's request logger.

## When something is missing

Stop the app and break it on purpose. First, boot as production, where the
generated `.envs/.env.production` deliberately leaves every secret blank:

```sh
APP_ENV=production pnpm start
```

```txt
TulipesBootError: Boot aborted during "environment" — 5 issue(s):
  ✖ [auth] required variable "JWT_ACCESS_SECRET" has no value (Signing key for short-lived access tokens)
  ✖ [auth] required variable "JWT_REFRESH_SECRET" has no value (Signing key for refresh tokens; separate from the access key so leaking one cannot mint the other)
  ✖ [auth] required variable "AUTH_ADMIN_EMAIL" has no value (Email of the admin account seeded on first boot)
  ✖ [auth] required variable "AUTH_ADMIN_PASSWORD" has no value (Password for the seeded admin account; change it after the first login)
  ✖ [core] required variable "REDIS_URL" has no value (Redis connection string (queues, cache, rate limits))
```

Read it in three parts. The **phase** (`environment`) is how far the boot
got: no module code has run, nothing has connected. The **count** is every
problem in that phase, not just the first. Each line names the **module**
that declared the variable and repeats its description, so you know who
needs it and why. `MONGO_URI` is absent from the list because the core module
can also build the connection from `MONGO_HOST` and friends, which have
defaults.

Now give the app a MongoDB address where nothing listens:

```sh
MONGO_URI=mongodb://127.0.0.1:27999/bookstore pnpm start
```

```txt
TulipesBootError: Boot aborted during "providers" — 2 issue(s):
  ✖ database connection failed (config.mongoose.uri): connect ECONNREFUSED 127.0.0.1:27999
  ✖ settings database connection failed (config.mongoose.uri): connect ECONNREFUSED 127.0.0.1:27999
```

This time the environment passed and the boot reached the providers phase.
Both providers that use MongoDB report, and each names the config key it
read the address from. The app never started listening, so a load balancer
would never send it traffic.

<Aside type="tip">
The full list of phases, and what each one checks, is on the
[boot pipeline](/tulipes-js/concepts/boot-pipeline/) page. The generated
skill `.claude/skills/tulipes-boot-errors/SKILL.md` is a field guide to
these reports.
</Aside>

## Where we are

We have a running app with nine modules and nothing of our own yet. The
`bookstore` directory is the project for the rest of the tutorial; keep
MongoDB and Redis running.
