A Tulipes app runs in production exactly as it runs on your laptop: `node app.ts`, with no transpile step and no bundle. What changes is the deployment around it: which processes you start, which `APP_ENV` they read, where secrets come from, and how the process is stopped. This page walks through each of those for the production preset, the app `tulipes init --preset production` generates from the reference app in `example/`.

## The processes

One codebase boots in different [process modes](/tulipes-js/concepts/process-modes/). Each entrypoint is one line that calls `boot()` with its mode:

```ts title="app.ts"
import { boot } from "@tulipes/core/boot";

await boot({ rootDir: import.meta.dirname, mode: "backend" });
```

```ts title="worker.ts"
import { boot } from "@tulipes/core/boot";

// Worker mode refuses to start until at least one module registers a
// queue processor — a consumer with nothing to consume is a
// misconfigured deployment, not a valid idle state.
await boot({ rootDir: import.meta.dirname, mode: "worker" });
```

| Process | Entrypoint | Script | What it does |
|---|---|---|---|
| backend | `app.ts` | `pnpm start` | Mounts the module routers, attaches Socket.IO, listens on `PORT` |
| worker | `worker.ts` | `pnpm worker` | Runs one BullMQ worker per registered processor; starts no HTTP server |
| mcp | `mcp.ts` | `pnpm mcp` | `serveMcp()` from `@tulipes/mcp`: boots in script mode and serves the modules' agent actions over stdio, or Streamable HTTP on its own port |

You need the worker as soon as any module has a `queues/*.queues.ts` file that calls `queues.process()`; jobs added by the backend wait in Redis until a worker consumes them. A worker started with no processors stops with `worker mode started with zero processors — no module registered queue work`.

The MCP process is optional and experimental (see [support policy](/tulipes-js/production/upgrading/)). Run it only if agents outside the app call its actions; the [MCP guide](/tulipes-js/guides/mcp/) covers its configuration.

## Node 24, no tsx

Since 0.11, Node strips TypeScript types natively, so the entrypoints run with `node` itself. The generated `package.json` pins the engine and uses node for every script:

```json title="package.json"
"scripts": {
  "start": "node app.ts",
  "worker": "node worker.ts",
  "mcp": "node mcp.ts",
  "script": "node"
},
"engines": {
  "node": ">=24.0.0 <25"
}
```

Three compiler flags make this work: `allowImportingTsExtensions`, `rewriteRelativeImportExtensions` and `erasableSyntaxOnly`. The last one refuses the syntax that type stripping cannot erase: parameter properties, `enum` and runtime `namespace`s. An app generated before 0.11 is moved over by `tulipes migrate 0.11`; the steps are on the [upgrading page](/tulipes-js/production/upgrading/).

The supported runtime is Node `>=24.0.0 <25`. CI tests 24.0.0 and the latest 24.x on Ubuntu with MongoDB 8 and Redis 7. Other Node lines and Windows are not claimed as supported. The CLI refuses a Node that cannot strip types with `Tulipes apps need Node 24 (or 22.18+)`.

## APP_ENV and the environment files

`APP_ENV` is the deployment axis, deliberately separate from `NODE_ENV`. It accepts `development`, `staging`, `production` or `test`, and defaults to `development` when unset. Any other value stops the boot:

```txt
APP_ENV "prod" is invalid — expected one of: development, staging, production, test
```

It decides three things at once:

- which file supplies environment values: `.envs/.env.<APP_ENV>`;
- which settings file core's file store uses when no settings provider is declared: `config/settings.<APP_ENV>.json`;
- whether a 500 response carries the real error message (development only).

Each module declares the variables it needs in its `package.json` under `tulipes.env`. A value resolves from **`process.env`, then `.envs/.env.<APP_ENV>`, then the declared default**, so values injected by a container or a process manager always win over the file. Every missing or invalid value is reported at once, and a `secret` is never printed. The full list is in [environment variables](/tulipes-js/reference/topics/environment-variables/).

<FileTree>
- .envs/ not committed; .gitignore excludes the whole directory
  - .env.development
  - .env.staging
  - .env.production
- .env.example generated by `tulipes sync`; the committed contract
</FileTree>

The reference app's production file is mostly blanks on purpose:

```sh title=".envs/.env.production"
PORT=3000
LOG_LEVEL=info

# MONGO_URI=
# REDIS_URL=
# JWT_ACCESS_SECRET=
# JWT_REFRESH_SECRET=
# AUTH_ADMIN_EMAIL=
# AUTH_ADMIN_PASSWORD=
```

Inject the connection strings and secrets through the host's environment or a secret store. Before the first start, check what the process will see:

```sh
APP_ENV=production pnpm check     # tulipes env:check: every value, where it came from, secrets withheld
```

<Aside type="caution" title="Development credentials are refused">
In `staging` and `production` the auth module's `credentials.bootstrap.ts` refuses blank or scaffold placeholder values for `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `AUTH_ADMIN_EMAIL` and `AUTH_ADMIN_PASSWORD`, and identical access and refresh keys. The boot stops with `Unsafe production credentials: configure JWT_ACCESS_SECRET, …`, naming the variables. Generate two distinct random keys and an operator-owned admin identity.
</Aside>

Values that are not secrets and not needed before the database answers are **settings**, not environment values: the public domain, proxy trust, CORS, HSTS, body limit and rate limits. In the production preset they live in MongoDB and are changed through `PATCH /config/:module`, which applies them live in every replica. See [settings](/tulipes-js/guides/settings/).

## MongoDB and Redis

The production preset declares four providers in its root `package.json`:

```json title="package.json"
"tulipes": {
  "providers": {
    "models": "@tulipes/mongoose",
    "settings": "@tulipes/mongoose/settings",
    "queues": "@tulipes/bullmq",
    "sockets": "@tulipes/socket.io"
  }
}
```

So every process needs both services reachable:

| Service | Variables | Used for |
|---|---|---|
| MongoDB 8 | `MONGO_URI`, or `MONGO_HOST` + `MONGO_USERNAME` + `MONGO_PASSWORD` + `MONGO_DBNAME` | Models, sessions, the `settings` collection, `config_audit_events` |
| Redis 7 | `REDIS_URL` (required) | Queues, the app cache, the shared auth session cache, rate-limit counters |

`MONGO_URI` wins over the parts when set, and is the only way to name a replica set, an Atlas `mongodb+srv://` cluster or driver options. A multi-host replica-set URI (`mongodb://a:27017,b:27017/db?replicaSet=rs0`) is accepted as long as every host parses on its own.

A replica set is not required, but it changes two things. Settings written in one process reach the others through a change stream (about 2 ms in the recorded failure run) instead of the 2-second poll used on a standalone server. And settings audits are written with majority acknowledgment, which on a replica set means a majority of members.

What happens when a service fails was measured against a three-node replica set in `docs/design/failure-evidence.md`:

| Scenario | Observed |
|---|---|
| Primary killed during a refresh rotation | the client got 200; the driver completed the write on the new primary |
| Redis down, rate-limited endpoint | 503 `RATE_LIMIT_UNAVAILABLE`; the limiter fails closed |
| Redis down, endpoint outside the limiter | 200; the cache degrades to a miss |
| Redis restarted | the limiter resumed within about 1 s |
| SIGTERM with a replica-set member down | exit code 0 in about 16 ms |

## Health checks

The minimal preset ships a public health endpoint in its `hello` module:

```ts title="modules/hello/routes/web.hello.health.routes.ts"
import { Router } from "express";
import type { BackendCtx } from "@tulipes/core/boot";
export default function healthRoutes({ rai, routes }: BackendCtx): void {
  const router = Router();
  router.get("/health", rai({ id: "hello:web:health", name: "Health" }), (_req, res) => {
    res.respond({ data: { status: "ok" } });
  });
  routes.mount(router, "");
}
```

It is mounted at the root (`routes.mount(router, "")`), not under the API prefix, and its id is granted to `guest` in `module.acl.ts`, so a load balancer can call `GET /health` without a token.

<Aside type="note">
The production preset (the reference app) has no `/health` route. Add one the same way in a module you own: a router mounted at `""`, a `rai()` id, and a `guest` grant. A process that answers it has finished every boot phase, because the backend only listens after the routers are mounted.
</Aside>

## Graceful shutdown

`boot()` installs handlers for `SIGINT` and `SIGTERM` (unless you pass `handleSignals: false`). On a signal it prints `[tulipes] SIGTERM — shutting down`, runs `handle.shutdown()`, and exits 0, or 1 if shutdown failed. The order matters:

```txt
SIGTERM
  └─ ctx.signal aborts          SSE streams and pollers end first
  └─ HTTP stops accepting       in-flight requests drain
  └─ providers drain            sockets close, workers finish jobs
  └─ bootstrap cleanups         in reverse load order
  └─ providers disposed         queues, then MongoDB last
```

The whole sequence shares one deadline, `shutdownTimeoutMs`, 10 seconds by default (a `boot()` option). A cleanup that fails or hangs is reported without preventing the ones after it, and a repeated signal joins the same shutdown instead of starting another. JavaScript cannot cancel a stuck job or a synchronous loop, so the process supervisor still owns final termination: give it a kill timeout at least as long as the shutdown deadline. That is why the [PM2 file](/tulipes-js/production/pm2/) sets `kill_timeout: 10000`.

## More than one replica

The generated PM2 file runs one instance of each process in fork mode. Before you add a second backend, consider what is shared and what is not:

- **Shared already:** settings (every replica applies a write), the auth session cache (Redis, so a logout on one replica is refused on all), and rate-limit counters (Redis, when replicas use the same `security.rateLimits.namespace`).
- **Not shared:** Socket.IO. The `@tulipes/socket.io` provider does not configure an adapter, so a second instance needs sticky sessions or a Socket.IO Redis adapter before clients can be spread across replicas.
- **Run per instance:** every `bootstrap/*.bootstrap.ts` file runs in every process at every boot. Bootstraps must be idempotent (the reference app's are); seeding the admin twice must be harmless.
- **Log stream caps are local:** the settings log stream allows four streams per controller and two per account, per process, not across replicas.

No multi-replica load run has been recorded for this framework yet; treat replica counts as something to test in staging.

## Logs

There are two layers of logs in the production preset.

The app's logger (pino, in `modules/core/helpers/logger/`) writes JSON lines under `LOG_DIR` (default `logs`) when `LOG_FILE` is true: an all-levels file `app-<mode>` and an errors-only file `error-<mode>`, rotated daily or at 20 MB, keeping 14 rotated files. `LOG_CONSOLE` (default true) adds pretty output on stdout; turn it off where a collector reads files only. `LOG_LEVEL` (default `info`) is the lowest level that reaches any destination.

PM2 captures each process's stdout and stderr in its own files (`logs/backend-out.log`, `logs/worker-error.log` and so on) and `pnpm pm2:logs` tails them.

The `settings` module's log stream lets a `sysadmin` read and tail the log files over SSE, bounded by the S08h limits in the [security model](/tulipes-js/production/security-model/). Keep the `sysadmin` role separate from ordinary administrators.

## A deployment, step by step

<Steps>
1. Provision MongoDB 8 and Redis 7, and give the app a database user with only the rights it needs.
2. Install Node 24 and pnpm 10 on the host, check out the app, and run `pnpm install --frozen-lockfile`.
3. Provide the environment: `APP_ENV=production` plus `MONGO_URI`, `REDIS_URL`, the two JWT keys and the admin identity. Run `APP_ENV=production pnpm check`.
4. Start the processes: `pnpm pm2:start:production`. See [PM2](/tulipes-js/production/pm2/).
5. Set `core.publicDomain` and `security.trustProxyCidrs` through `PATCH /config/core` and `PATCH /config/security`, then install the nginx site. See [nginx](/tulipes-js/production/nginx/).
6. Install a TLS certificate, enable the TLS block, and close the app port to everything but loopback.
7. Work through the [production checklist](/tulipes-js/production/checklist/).
</Steps>
