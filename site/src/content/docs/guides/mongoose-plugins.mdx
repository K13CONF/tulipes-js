The production preset gives every model the same cross-cutting behavior:
`created_at` and `updated_at` timestamps, soft deletion that keeps deleted
rows out of ordinary queries, and clean JSON serialization. None of it is in
the framework. It is application code in the sys core module, exported from
`@app/core`, so you read it, change it and extend it like any other module.

## What is there

<FileTree>
- modules/core/helpers/mongoose/
  - index.ts baseSchemaOptions, re-exports
  - register.ts registerBasePlugins()
  - plugins/
    - base.plugin.ts baseModelPlugin: composes the two below
    - timestamps.plugin.ts timestampsPlugin
    - soft-delete.plugin.ts softDeletePlugin
    - types.ts Timestamps, SoftDeleteFields, SoftDeleteMethods, BaseDocument, Actor
</FileTree>

Everything is exported from the module's `lib/index.ts`:

```ts
import {
  baseSchemaOptions, baseModelPlugin, softDeletePlugin, timestampsPlugin, registerBasePlugins,
  type Actor, type BaseDocument, type SoftDeleteFields, type SoftDeleteMethods, type Timestamps,
} from "@app/core";
```

## `registerBasePlugins()`: global, and early

Global Mongoose plugins only apply to schemas compiled **after** they are
registered. Models compile in boot phase 5, so registration has to happen
before that, in every process. The core module's `module.config.ts` does it,
because declarations load in phase 4:

```ts title="modules/core/module.config.ts"
import { registerBasePlugins } from "./helpers/mongoose/index.ts";

/**
 * Declaration time (boot phase 4) is before models compile (phase 5), which
 * is exactly when a global mongoose plugin has to exist: registering here
 * makes the base plugins apply in EVERY mode — backend, worker and script
 * alike — so a script can never read rows the API considers deleted.
 */
registerBasePlugins();
```

```ts title="modules/core/helpers/mongoose/register.ts"
let registered = false;

export function registerBasePlugins(): void {
  if (registered) return;
  registered = true;
  mongoose.plugin(baseModelPlugin);
}
```

It is an explicit function rather than an import side effect, so correctness
does not depend on import order, and it is idempotent, so a second call is
harmless. It works because the app and `@tulipes/mongoose` share one
`mongoose` instance.

<Aside type="caution">
Do not move the call to `app.ts`. Scripts and the worker have their own
entrypoints, and a model compiled without the plugin would return
soft-deleted rows. The core module runs in every process, which is why the
call lives there.
</Aside>

## `baseModelPlugin`

The one plugin registered globally. It composes the focused plugins so each
stays single-purpose:

```ts title="modules/core/helpers/mongoose/plugins/base.plugin.ts"
export function baseModelPlugin(schema: Schema): void {
  schema.plugin(timestampsPlugin);
  schema.plugin(softDeletePlugin);
}
```

New cross-cutting behavior (an audit trail, versioning) slots in here without
touching a single model.

## `timestampsPlugin`

Mongoose-managed timestamps, with the field names the API uses on the wire:

```ts title="modules/core/helpers/mongoose/plugins/timestamps.plugin.ts"
export function timestampsPlugin(schema: Schema): void {
  schema.set("timestamps", {
    createdAt: "created_at",
    updatedAt: "updated_at",
  });
}
```

Mongoose fills `created_at` on create and `updated_at` on every save or
update. Never declare `createdAt`/`updatedAt` (or `timestamps: true`) in a
model: you would get a second, camelCase pair.

## `softDeletePlugin`

Soft deletion: a document is flagged rather than removed, and ordinary queries
stop returning it.

### Fields it adds

| Field | Type | Live value |
|---|---|---|
| `is_deleted` | `Boolean`, indexed | `false` |
| `deleted_at` | `Date` | `null` |
| `deleted_by` | `{ model, id }` or `null` | `null` |

`deleted_by` is a polymorphic actor: `model` is a model name (`"User"`) and
`id` its `_id`, with `refPath`, so `.populate("deleted_by.id")` resolves it.

### What it filters

| Operation | Soft-deleted documents |
|---|---|
| `find*`, `count*`, `distinct` | excluded |
| `update*`, `replace*` | excluded: you cannot update a deleted row by accident |
| `aggregate` | excluded: a `$match` is prepended to the pipeline |
| `deleteOne`, `deleteMany` | **not** filtered: when code says delete, it deletes |

The filter is `{ is_deleted: { $ne: true } }`, so legacy documents with no
`is_deleted` field count as live. It is skipped when the query already names
`is_deleted`, or when the caller opts out.

### Methods and statics

```ts
await doc.softDelete(actor);                    // flag one document and save
await doc.restore();                            // clear the flags and save
await Model.softDelete({ team: id }, actor);    // flag many (updateMany)
await Model.restore({ team: id });              // restore many, deleted rows included

Model.find().withDeleted();                     // live and deleted
Model.find().onlyDeleted();                     // deleted only
```

`actor` is optional: `{ model: "User", id: user._id }`.

The users back office uses both sides. Soft-deleting an account:

```ts title="modules/users/controllers/bo.users.controllers.ts"
const user = await this.#ctx.models!.get("User").findOne({ email: req.params.email });
if (!user) throw new HttpError(404, "notFound");

await forgetUser(this.#ctx, String(user._id));
await (user as unknown as { softDelete(): Promise<unknown> }).softDelete();
res.respond({ data: { email: req.params.email, soft_deleted: true } });
```

And listing deleted accounts, opting out of the filter:

```ts title="modules/users/controllers/bo.users.controllers.ts"
const deleted = await this.#ctx.models!
  .get("User")
  .find({ is_deleted: true })
  .setOptions({ withDeleted: true } as Record<string, unknown>)
  .select("email role -_id")
  .lean();
```

The casts are there because the plugin adds its members at runtime: the
schema in the model file does not declare them, so the generated model type
does not know them. Type them by extending `BaseDocument` (below), or use
`setOptions({ withDeleted: true })` as here, which needs no typing.

<Aside type="note">
The [list-query language](/tulipes-js/guides/pagination-and-list-queries/)
relies on this plugin: soft-deleted rows never appear in a list, count or
group, so no endpoint has to add the condition. One consequence: `$text`
search with `group` fails on a soft-deleting model, because MongoDB requires
`$text` in the first pipeline stage and the plugin's `$match` comes first.
</Aside>

## `baseSchemaOptions`

Serialization conventions every model spreads into its schema options:

```ts title="modules/core/helpers/mongoose/index.ts"
export const baseSchemaOptions: SchemaOptions = {
  toJSON: {
    versionKey: false,
    transform: (_doc, ret: Record<string, unknown>) => {
      delete ret._id;
      return ret;
    },
  },
};
```

```ts title="modules/hello/models/greeting.model.ts"
const greetingSchema = new Schema({ /* fields */ }, baseSchemaOptions);
```

`toJSON` drops `__v` and `_id` when a **document** is serialized. A `.lean()`
query returns plain objects, which `toJSON` never sees, so the reference app's
handlers project explicitly: `.select("email role -_id")`. Timestamps are not
set here; the plugin owns them.

To add schema options of your own, spread the base first:

```ts
new Schema(fields, { ...baseSchemaOptions, collection: "invoices_v2" });
```

## Types

```ts title="modules/core/helpers/mongoose/plugins/types.ts"
export type BaseDocument<T = ObjectId> = Document<T> &
  Timestamps &
  SoftDeleteFields &
  SoftDeleteMethods;
```

Extend it when you write a document interface by hand, to get the fields and
methods typed:

```ts
import type { BaseDocument } from "@app/core";

export interface InvoiceDoc extends BaseDocument {
  number: string;
  amount_cents: number;
}
```

`BaseDocument<string>` overrides the `_id` type.

## Adapting the plugins

The plugins are yours. Common changes:

- **Add a plugin to every model**: write it next to the others and add one
  `schema.plugin(...)` line to `baseModelPlugin`.
- **Add a plugin to one model**: call `schema.plugin(myPlugin)` in that model
  file, before the default export.
- **Rename the timestamp fields**: change `timestampsPlugin`. Existing
  documents keep the old keys, so ship a `$rename` in a bootstrap task too.
- **Make deletes soft by default**: the plugin deliberately leaves
  `deleteOne`/`deleteMany` literal. Call `softDelete` instead in your code
  rather than overriding hard deletes.

Fixes to these files in a generated app ship as migration steps in the
framework's upgrade notes, not as library updates, because the code is the
app's. See [upgrading](/tulipes-js/production/upgrading/).
