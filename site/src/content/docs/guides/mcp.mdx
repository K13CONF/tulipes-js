The [Model Context Protocol](https://modelcontextprotocol.io) is how Claude Code,
Claude Desktop and other agent clients discover and call tools. `@tulipes/mcp`
turns a Tulipes app into an MCP server: `tools/list` is the
[agent manifest](/tulipes-js/guides/agents/) for the caller, and `tools/call` runs
an action through `ctx.agent.invoke()`, so the ACL, the credential's scopes and
the input schemas decide exactly as they do over HTTP. You choose how the caller
is identified, in one function.

<Aside type="caution" title="Experimental">
`@tulipes/mcp` and the agent surface it serves are outside the compatibility
promise: flags, tool naming and the manifest may change in any release without a
deprecation period.
</Aside>

## Two ways to serve

| | `pnpm mcp` (`serveMcp`) | `tulipes-mcp` (the bridge) |
|---|---|---|
| runs | the app itself, booted in script mode | a thin proxy, no app code |
| reaches the app | in process, `ctx.agent` | over HTTP, the agent door |
| identity | `config/mcp.config.ts` `identify()` | the bearer token sent to the door |
| transports | stdio, or Streamable HTTP | stdio |
| needs | the database and the app's environment | a running backend |

Prefer `pnpm mcp`. The bridge exists for apps that do not want a second process
with database access on the host, and is the first thing to be removed if nobody
uses it.

## The MCP process

Apps generated by `tulipes init` on 0.13 or later have it already; an older app
gets it with `tulipes migrate 0.13`, which adds `mcp.ts`,
`config/mcp.config.ts`, the `mcp` script and the `@tulipes/mcp` dependency.

```ts title="mcp.ts"
import { serveMcp } from "@tulipes/mcp";

// The app as an MCP server: boots in script mode and serves the actions
// modules declare in agent/*.agent.ts to the caller config/mcp.config.ts
// identifies.
await serveMcp({ rootDir: import.meta.dirname });
```

```json title="package.json"
{ "scripts": { "mcp": "node mcp.ts" } }
```

`serveMcp(options)` boots the app with `mode: "script"` (every phase, no HTTP
server, no worker), reads `config/mcp.config.ts`, opens the transport and serves.
Its options:

| Option | Meaning |
|---|---|
| `rootDir` | the app root, holding `modules/` and `config/` |
| `argv` | defaults to `process.argv.slice(2)`; `--token <credential>` is read from it |
| `transport` | a custom MCP SDK transport instead of the configured one (tests use an in-memory one) |
| `audit` | where audit lines go; stderr by default |

It resolves to an `McpProcess` with `handle` (the boot handle), `server` or
`http` and `url`, and `close()`. When the stdio client closes its input, the
server closes and the app shuts down, so the process exits instead of lingering.

## config/mcp.config.ts

```ts title="config/mcp.config.ts"
import { defineMcp } from "@tulipes/mcp";

import { identifyCredential } from "../modules/auth/lib/index.ts";

export default defineMcp({
  transport: "stdio",
  identify: (ctx, credential) => identifyCredential(ctx, credential),
});
```

`defineMcp({ transport?, identify? })` is the default export. Without the file,
every caller is a guest on stdio.

### identify(ctx, credential)

`identify` answers one question: who is calling. It receives the runtime context
and the credential the client presented, and returns a `ToolActor` (an `Auth`
plus a `role`) or `null` for a guest. It runs on **every** list and call, so a
revoked token or a role change applies to a session that is already open.

- **Production preset.** `identifyCredential()` from the auth module resolves an
  [API token](/tulipes-js/guides/api-tokens-and-scopes/) or an access JWT as a
  request's bearer is resolved: the role from the user, the scopes from the token,
  `null` once revoked. Give an agent a scoped API token rather than your access
  token, which expires in 15 minutes.
- **Minimal preset.** There is no auth module, so the role comes from an
  environment variable:

  ```ts title="config/mcp.config.ts (minimal preset)"
  import { defineMcp, developmentIdentity } from "@tulipes/mcp";

  export default defineMcp({
    transport: "stdio",
    identify: developmentIdentity("MCP_ROLE"),
  });
  ```

  `developmentIdentity(variable = "MCP_ROLE")` returns an authenticated actor with
  that role, or a guest when the variable is unset. It is refused at startup when
  `APP_ENV` is `production` or `staging`:

  ```txt
  config/mcp.config: developmentIdentity() reads the role from MCP_ROLE, which is refused when APP_ENV is production — identify callers from a credential
  ```

- **Your own.** Any function with that signature works: look up a key in your own
  table, call your identity provider. Return `null` for anything you do not
  recognise.

### transport

**`"stdio"`** (the default): one client, the one that started the process. The
credential is `--token <credential>` or `TULIPES_MCP_TOKEN`. stdout belongs to the
protocol, so everything the app logs is moved to stderr.

**`{ http: { port, host?, path?, maxBodyBytes? } }`**: MCP's Streamable HTTP,
stateless, for remote agents. Each POST gets its own server bound to the actor its
`Authorization: Bearer` header identifies, so two clients never share an identity.

| Field | Default | Meaning |
|---|---|---|
| `port` | required | the port; `0` picks a free one |
| `host` | `127.0.0.1` | the bind address |
| `path` | `/mcp` | the endpoint; anything else answers 404 |
| `maxBodyBytes` | `1048576` | larger bodies get 413 before `identify` runs |

```ts title="config/mcp.config.ts"
export default defineMcp({
  transport: { http: { port: 3100 } },
  identify: (ctx, credential) => identifyCredential(ctx, credential),
});
```

The endpoint accepts only POST (405 otherwise), sets no CORS headers and reads no
cookies: it is a machine endpoint. Without `identify`, the HTTP transport refuses
to start in production or staging:

```txt
config/mcp.config: the http transport has no identify, which would serve every caller on the network as a guest — refused when APP_ENV is production
```

On a loopback bind (`127.0.0.1`, `localhost`, `::1`) it answers only requests
whose `Host` is its own address, and 403 otherwise. That defeats DNS rebinding,
where a web page re-points its own name at your machine.

<Aside type="caution">
The production nginx template carries a commented `location = /mcp` block that
proxies to `127.0.0.1:3100` with `proxy_set_header Host $host`. With the default
loopback bind, that public `Host` is refused by the check above. If you expose MCP
through nginx, either forward the listener's own address as the Host header or
bind another `host` and keep the port closed to the outside. Test the path before
relying on it.
</Aside>

## Connect Claude Code

<Steps>

1. Issue a scoped API token for the agent (production preset):

   ```sh
   curl -X POST http://localhost:3000/api/v1/auth/tokens \
     -H "authorization: Bearer $ACCESS_TOKEN" -H 'content-type: application/json' \
     -d '{"name":"claude-code laptop","scopes":["hello:web:*"]}'
   ```

2. Register the server with the token in the environment, never on the command
   line, where `ps` would show it:

   ```sh
   claude mcp add tulipes-example -e TULIPES_MCP_TOKEN="$TOKEN" -- pnpm --silent mcp
   ```

   `--silent` keeps pnpm's own banner off stdout, which belongs to the protocol.

3. Start Claude Code in any directory and ask it to list the app's tools. The
   process prints its identity on stderr when it starts:

   ```txt
   [tulipes] mcp mode · stdio · user · scopes hello:web:*
   ```

</Steps>

Any MCP client that can start a command works the same way: the command is
`pnpm --silent mcp` in the app's directory, with `TULIPES_MCP_TOKEN` in its
environment. For the HTTP transport, point the client at
`http://127.0.0.1:3100/mcp` and have it send `Authorization: Bearer <token>`.

## What the client sees

- **Server instructions** name the app and list each module's `summary`.
- **`tools/list`** is `ctx.agent.manifest(actor)`, re-read on every list, so a
  role change or a redeploy shows up without restarting the client. Each tool has
  its JSON Schema input and `annotations.readOnlyHint` from the action's
  `readOnly`.
- **`tools/call`** returns `{ data }` as text, plus `structuredContent` when the
  data is an object. A refusal (the role changed since the last list, the input
  failed its schema) comes back as a tool error the agent can read, not as a
  crash, in the form `<status>: <message> (<code>)`:

  ```txt
  403: role "user" may not hello:bo:greetings:reset (FORBIDDEN)
  ```

  A name that was not in the last list answers
  `no tool named "x" — list tools again`.

## Auditing

Every call writes one JSON line to stderr: the tool, the actor's user id (or
`guest`), the credential id when it is an API token, the role, the outcome and
the duration. Never the input.

```json
{"mcp":"call","tool":"hello_web_greetings","actor":"6720…","credential":"3f9c0a1b2c3d4e5f","role":"user","outcome":"ok","ms":12}
```

Outcomes are `ok`, `refused <CODE>` and `failed` (an unexpected error, whose
stack follows on stderr). Collect stderr wherever you keep logs.

## The tulipes-mcp bridge

The bridge runs no app code. It reads the manifest from the
[agent door](/tulipes-js/guides/agents/#the-agent-door-http) and runs each call at
`POST <url>/tools/<name>`, sending the same bearer token every time, so the app's
own auth and ACL decide.

<Tabs syncKey="pkg">
  <TabItem label="pnpm">
    ```sh
    pnpm add -D @tulipes/mcp
    pnpm tulipes-mcp --url http://localhost:3000/api/v1/agent --token "$TOKEN"
    ```
  </TabItem>
  <TabItem label="npm">
    ```sh
    npm install -D @tulipes/mcp
    npx tulipes-mcp --url http://localhost:3000/api/v1/agent --token "$TOKEN"
    ```
  </TabItem>
</Tabs>

| Flag | Environment | Default |
|---|---|---|
| `--url <agent door>` | `TULIPES_URL` | `http://localhost:3000/api/v1/agent` |
| `--token <bearer>` | `TULIPES_TOKEN` | none: calls as guest |

```sh
claude mcp add tulipes-example -e TULIPES_TOKEN="$TOKEN" -- pnpm tulipes-mcp
```

## In code

The pieces are exported for other hosts:

```ts
import { AgentBridge, createServer } from "@tulipes/mcp";

const bridge = new AgentBridge({ url: "http://localhost:3000/api/v1/agent", token });
const server = await createServer(bridge);
await server.connect(transport); // any @modelcontextprotocol/sdk transport
```

`createServer(source, { name?, version? })` also accepts a `ToolSource`
(`{ manifest(), call(tool, input) }`) of your own.

## Security

- **The MCP process is the app.** It has the database and every secret the app
  has, and acts with whatever role `identify` returns. Treat the machine it runs
  on accordingly.
- **Identify from a credential in production.** `developmentIdentity()` and an
  HTTP transport without `identify` are both refused in production and staging.
- **Scope the token.** A scope never widens a role; it lets you hand an agent less
  than you hold. `OUT_OF_SCOPE` refusals tell you when it needs more.
- **Revoke by name.** `DELETE /auth/tokens/:token_id` takes effect on the next list
  or call, because `identify` runs every time.
- **Mark actions honestly.** `readOnlyHint` comes from `readOnly`; clients use it
  to decide what to run without asking.
- **Keep tokens out of argv and URLs.** Use `TULIPES_MCP_TOKEN` or `TULIPES_TOKEN`.
