# Tulipes example app

The reference layout for a Tulipes application. Everything in this folder is
**yours** — the framework itself lives in `@tulipes/core` and you never edit it.

## Layout — what every piece is for

```
example/
├── app.ts                  backend entrypoint      — boot({ mode: "backend" }), ~3 lines
├── worker.ts               worker entrypoint   — boot({ mode: "worker" })
├── config/
│   └── app.config.ts       app-wide config seed, runs before every module factory
├── modules/                the app itself: one folder = one feature = one package
│   ├── core/               tier "sys" — infra env vars, global roles, and the
│   │                       shared helpers (cache, mongoose plugins) other
│   │                       modules import as `@app/core`
│   ├── auth/
│   └── users/
├── scripts/                one-off tasks — boot in script mode, no server
├── nginx/                  per-env site templates for scripts/deploy-nginx.ts
├── locales/                i18n dictionaries (planned)
├── CLAUDE.md               rules for AI agents working in this project
├── .claude/skills/         task-scoped skills (module, endpoint, model, queue…)
├── types/
│   └── config.d.ts         GENERATED by `tulipes sync` — do not edit
├── .envs/
│   └── .env.development    per-mode env files; APP_ENV picks one
├── .env.example            GENERATED — every variable any module declares
└── tsconfig.json
```

### Where does global middleware go?

In sys modules — there is no separate mechanism. Sys modules load before
every app module, so a sys module's routes file mounting on `ctx.app` IS the
"before all routes" slot:

- **`modules/core/`** (sys, priority 0 — the very first router): request
  ids, cross-cutting glue like the cache demo. Anything that must run before
  absolutely everything goes here.
- **`modules/security/`** (sys, priority 10): the hardening stack — security
  headers, pino request logging (pretty in development, JSON lines in
  production, level via its LOG_LEVEL variable), body parsing with a size
  cap. Implementations live in this module's `helpers/`, not the framework.

The backend request pipeline, in order:

```
1. module routers      load order — sys first:
     core (sys, 0)        request id → cache glue
     security (sys, 10)   headers → pino logger → json parsing
     auth, users… (app)   feature routes
2. notFoundHandler     core — turns the rest into a 404
3. errorHandler        core — terminal; catches async throws, hides
                       internals outside development
```

Core only guarantees the fail-closed tail (2–3). Everything else is modules.
Middleware for **one module only** doesn't belong in a sys module — mount it
on that module's own Router inside its `*.routes.ts`.

### Where does app-wide config go?

`config/app.config.ts` — its result seeds the global config *before* any
module factory runs, so every module can read it (`ctx.config.app.name`).
Config that belongs to one module goes in that module's `module.config.ts`.

### Where do shared helpers go?

Into a module — there is no top-level `lib/`. Helpers that more than one
module needs belong to the sys `core` module, exported from its `index.ts`
and imported by package name:

```ts
import { baseSchemaOptions } from "@app/core";
```

That keeps the coupling visible: a module using them declares `@app/core`
in its `dependencies` and `"core"` in `dependsOn`, so the dependency is in
package.json instead of hidden in a relative path.

Two live examples ship inside `modules/core/helpers/`:

- **`logger/`** — pino with two destinations at once: coloured and
  human-readable on the console, JSON lines in `logs/` for querying, plus
  an errors-only file. Log file names carry the process mode, since
  backend and worker run together and would otherwise rotate the same
  file. Use it as `moduleLogger(env, "users", mode)` — the module name
  shows as `[users]` on the console and as a queryable field in the files.
- **`cache/`** — a small `Cache` contract with two drivers: `RedisCache`
  (JSON-serialized, key-prefixed so it never collides with BullMQ) and
  `MemoryCache` (LRU-capped, for tests and redis-less runs). `appCache(env)`
  picks the driver from the environment; the core module's `onShutdown`
  closes it.
- **`mongoose/`** — plugins every model gets via `registerBasePlugins()`,
  called from the core module's `module.config.ts` (phase 6, before models
  compile in phase 8, so it covers scripts too): snake_case
  `created_at`/`updated_at`, and soft delete — `doc.softDelete(actor)` flags
  instead of removing, ordinary queries auto-exclude flagged docs,
  `.withDeleted()` / `.onlyDeleted()` opt out, and hard `deleteOne` stays
  literal on purpose. Extend `BaseDocument` in model interfaces to inherit
  the typed fields and methods.

## Anatomy of a module

```
modules/users/
├── package.json            name + "tulipes" key: tier / priority / dependsOn
├── meta.variables.json     every env variable this module needs (validated at boot)
├── module.config.ts        default-export: config factory; optional onReady/onShutdown
├── module.acl.ts           permission grants for this module's resources
├── routes/*.routes.ts      default-export (ctx) => Router
├── models/*.model.ts       default-export { name, schema }
├── bootstrap/*.bootstrap.ts  post-DB, pre-server tasks (indexes, seeds)
├── queues/*.queues.ts      default-export (ctx, queues) => define + process
├── sockets/*.sockets.ts    default-export (ctx, sockets) => claim namespaces
└── controllers/            convention only — routes import them directly
```

Modules load in order: tier `sys` first, then `priority` (lower first), then
`dependsOn` topological order. Every file above is optional except
package.json.

## Boot order (what runs when)

1. Environment: `.envs/.env.<APP_ENV>` + every `meta.variables.json` →
   validated variable store (crashes with ALL problems at once)
2. Module graph: sort + cycle detection
3. `config/app.config.ts` seed → every `module.config.ts` factory
4. ACL merge (roles from sys core, grants everywhere)
5. Database: connect → models → bootstrap tasks
6. Queues register (both modes)
7. **backend**: pipeline above, sockets, listen · **worker**: start consuming
8. `onReady` hooks — shutdown runs everything in reverse

## Daily commands

| command | does |
|---|---|
| `yarn dev` / `tulipes dev` | run backend process (dev regenerates types first) |
| `yarn worker` | run queue-consumer process |
| `tulipes sync` | regenerate `types/config.d.ts` + `.env.example` |
| `tulipes env:check` | validate env without booting — CI gate |
| `tulipes new module <name>` | scaffold a module |
| `yarn typecheck` | typecheck app against the generated types |
